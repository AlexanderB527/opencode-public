# Code Mode в OpenCode TestOps

Аудит публичного снимка `d181d945d1885667e2c9c3a469d12e01622538f4`. В снимке есть исходники двух плагинов, двух скиллов, 28 Python-файлов и пять схем. Внутренние эталоны, тестовые запуски, конфигурация рабочего хоста и собранный GUI исключены из публикации.

## Выявленная повторная работа

- `index.ts` для общего rerunPreview/rerun сначала делает brief, затем `collectTeamReruns`. Оба вызывают загрузку запуска и страниц результатов. Dispatch дополнительно запрашивает свежий снимок по своему контракту. Изменение общего Jenkins-пути за пределами MVP.
- GUI Analyze строит brief и передаёт статистику, предупреждения, инструкции и до 3000 символов @-списка в `session.prompt`. Основной скилл может заново сканировать запуск, а triage гарантированно вызывает собственные get_launch и scan_flat. Снимки JS и Python имеют разные контракты и правила применения, поэтому подстановка одного вместо другого требует доказательства эквивалентности.
- Brief догружает сообщения для отображаемого среза; triage отдельно читает детали для классификации по trace. Trace, нужный классификатору, должен остаться доступным внутри Python. Экономия MVP относится к дополнительному evidence и к объёму результата в контексте модели.
- TTL-кэш brief переиспользует завершённый снимок, но не объединяет одновременные промахи. Последовательность scan → проверка → рендер создаёт промежуточные результаты для модели. Число реальных дублей, итераций и токенов требует измерения.

## TO-BE

Модель → узкий tool OpenCode V2 → типизированный реестр адаптеров и фиксированный workflow → существующий JS brief либо Python triage → компактный результат. Отдельный evidence tool раскрывает ограниченную выборку из того же запуска по идентификатору снимка, привязанному к сессии. При явном типе запуска выбирается соответствующий pipeline. Auto сохраняет штатную эвристику и предлагает отдельный запрос триажа при обнаружении рерана.

Сводка передаёт тип и источник его определения, счётчики, признаки полноты/давности, предупреждения, группы и следующий доступный срез. Усечение отражается явным полем. Прерванные или частичные данные не участвуют в утверждениях о подтверждённой причине.

Операции реестра типизируются по входу/выходу и проверяют вход во время исполнения. Workflow собирается из доверенных функций плагина. Независимые чтения используют фиксированный пул, зависимые стадии запускаются последовательно. Один бюджет охватывает время, HTTP-вызовы, вывод и число активных операций. Отмена доходит до HTTPS-запроса и дочернего процесса. В Python-адаптере фиксированный исполняемый файл и argv, shell выключен, пути и рабочее окружение определяет хост. Для MVP предпочтителен вызов существующего `collect` через небольшой доверенный bridge без записи канонических файлов. Перед подключением нужно подтвердить паритет с CLI, включая гейты.

## Совместимость OpenCode

Манифест плагина фиксирует `@opencode/plugin@2.3.2`, сам runtime репозиторий не фиксирует. В опубликованных типах 2.3.2 подтверждены V2 tool API, `ToolContext.signal`, `codemode` у tool, учёт токенов и экспериментальный `full_codemode` (по умолчанию выключен). Текущая документация описывает `execute` с доступом к каталогу и встроенным HTTP fetch, поэтому включение общей среды расширяет поверхность. Локальный CLI после запуска с временной конфигурацией сообщил `opencode-ai@1.18.18`. Версию рабочего Desktop/server и фактическое поведение вложенных permissions следует подтвердить на целевом хосте.
