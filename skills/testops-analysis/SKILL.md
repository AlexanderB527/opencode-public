# TestOps: разбор упавших автотестов

> **Purpose**: провести упавшие автотесты от скана запуска до вердикта — кто упал,
> кто виноват, что конкретно чинить.

## Когда брать

- Разобрать запуск: «разбери упавшие», «анализ прогона», дали ссылку на launch и тип HF/QG/RM.
- Классифицировать результаты перезапуска: «разбор рерана», «отдели ошибки системы от дефектов».
- Разобрать причину конкретных тестов: «почему упал @10.05.03.01», «предложи решение».
- Раздать упавших на перезапуск: «раздай по командам», «перезапусти командные джобы».
- Спланировать автоматизацию техдолга TX/T9: «разложи техдолг по сложности»,
  «с чего начать техдолг», «что в группе TX-F» — ответ из готового реестра
  `references/techdebt-tx-t9.md` (см. § «Реестр техдолга»), без обращения к TestOps.

## Когда НЕ брать

- Задача не про падения автотестов: новые тест-кейсы, документация, UI-сценарии, код продукта.
- Нет доступа к TestOps API (`TESTOPS_TOKEN`) — сначала настройка окружения, `references/toolkit-guide.md`.
- Нет доступа к эталонам: кэш `~/.qa-artifacts/etalons` пуст, а доступа к `AUTOTEST/sfa` нет (git-креды) — эталоны тянутся из ветки `qa-analysis-data` (AUTOTEST/sfa).

## Режимы

| Режим | Reference | Что делает | Вход | Выход |
|---|---|---|---|---|
| Разбор запуска | `run-analysis.md` | Скан запуска, сверка @-списка с эталоном команды, статистика с процентами, публикация сводной страницы | Ссылка/ID launch, тип HF/QG/RM, команда(ы) | `expected_set.json`, статистика в чате, страница в Confluence |
| Раздача перезапусков | `dispatch.md` | Раскладка @-списков по КОМАНДНЫМ джобам `DEBUG/<TEAM>`, запуск сборок | `launch_id` со сделанным сканом | `dispatch.json`, страница «AI run», ссылки на сборки |
| Классификация перезапуска | `rerun-classifier.md` | Дифф рерана с первичным запуском, раскладка снова-упавших на три типа: система / автотест / дефект | ID rerun и первичного launch | Вердикт в чате по кластерам, `rerun_diff.json`, `rerun_classification.json` |
| Глубокий разбор | `deep-failure.md` | Корневая причина и решение по конкретным тестам | Список тестов (номера / названия / ID) или launch | Блок «Причина + Решение» на тест, статус подтверждённости |
| История и повторяющиеся причины | `toolkit-guide.md` (§ База результатов) | Что уже разбиралось по команде: частые кластеры причин, типовые фиксы, владельцы | Команда (+ тип, число последних прогонов) | Сводка из `index.json` / `causes.jsonl`, обновлённая база |
| Планирование техдолга TX/T9 | `techdebt-tx-t9.md` | Раскладка 149 тестов техдолга по сложности L1/L2/L3 и 22 паттерн-группам | Ничего / группа (`TX-F`) / уровень (`L2`) | Ответ из реестра, без TestOps |

Reference-файлы лежат в `references/`. Режим выбирается по запросу; вход неоднозначен
(тип, команда, launch, rerun) — спросить, не угадывать.

Как пользоваться и что ожидать (триггеры, примеры диалогов, что появляется на диске) —
`references/how_to.md`.

**Реестр техдолга.** Раскладка тестов техдолга TX и T9 по сложности (L1/L2/L3) и
паттернам — `references/techdebt-tx-t9.md`. Использовать, когда нужно спланировать
автоматизацию техдолга, выбрать порядок взятия тестов или сослаться на группу
(`TX-F`, `T9-B` …). Это справочник раскладки: статусы и причины падений берутся
из исходной таблицы, а не из него.

## Ветки данных (где что лежит)

Данные скилла живут в **одной** технической orphan-ветке `qa-analysis-data` репозитория
`AUTOTEST/sfa` (без кода автотестов), в двух каталогах:

| Данные | Каталог в ветке `qa-analysis-data` | Ссылка |
|---|---|---|
| Эталоны команд (13 команд × HF/QG/RM) | `etalons/<TEAM>/etalon_<тип>.txt` | https://example.invalid |
| Результаты разборов | `results/<TEAM>/` | https://example.invalid |
| Код скилла (этот PR) | — | https://example.invalid |

Ветка и каталоги заданы дефолтами в скриптах (`etalons_branch`/`etalons_path` =
`qa-analysis-data`/`etalons`, `results_branch` = `qa-analysis-data`) и переопределяются
в `~/.qa-artifacts/config.json` или env (`QA_ETALONS_BRANCH`, `QA_BRANCH`).

## База знаний разборов

Результаты разборов накапливаются в ветке `qa-analysis-data` (`AUTOTEST/sfa`, `results/<TEAM>/`):
`index.json` (последние прогоны + топ причин), `causes.jsonl` (агрегат), `launches/*.json` (сырьё).

- Перед разбором — прочитать базу команды: `fetch_results.py --team <TEAM>` (или `--all`),
  затем `index.json`. Это гипотезы и история, **не доказательства**: причину всё равно
  подтверждай evidence (реран, git, дефект).
- После рерана/глубокого разбора — опубликовать результат: `publish_results.py --push`
  (идемпотентно, только по подтверждению пользователя).
- Confluence — **опционально**: отчёт можно оставить в чате и в базе.

### Как именно пополняется

| Файл | Растёт как | Правило |
|---|---|---|
| `launches/<id>_<тип>.json` | +1 файл на каждый опубликованный прогон, **хранятся все** | перезапись только при повторной публикации того же прогона |
| `causes.jsonl` | +1 запись на новую пару `(номер теста, кластер)` | `seen_count` растёт только при **новом** `launch_id`; `first_seen` не перезаписывается; `confirmed` не понижается; `refuted` не повышается без подтверждения |
| `index.json` | пересобирается целиком | последние 10 прогонов + топ-15 активных кластеров (refuted исключены) |

**Что даёт прирост знаний:** только фазы rerun/deep. Первичный скан публикует цифры с
`causes: []` — знания не растут. Поэтому ценность базы = число разобранных реранов, а не
число прогонов.

### Автозапуск: дождаться прогона и разобрать сразу

`watch_launch.py` поллит TestOps и запускает разбор сам (ожидание в чате не используется —
каждый опрос стоил бы tool-call и токенов):

```powershell
# дождаться завершения, просканировать, собрать локально
py -X utf8 <QA_HOME>\scripts\watch_launch.py --launch-id 1327498 --teams "T9,TX" --type QG

# то же + публикация в базу
py -X utf8 <QA_HOME>\scripts\watch_launch.py --launch-id 1327498 --teams "T9,TX" --type QG --push

# дождаться ещё и рерана, классифицировать, опубликовать с причинами
py -X utf8 <QA_HOME>\scripts\watch_launch.py --launch-id 1327498 --teams "T9,TX" --type QG \
    --wait-rerun 1334823 --push
```

Готовность = счётчики (`total/passed/failed/broken/skipped`) не меняются `--stable` опросов
подряд (по умолчанию 2 × 90 с) **и** `total > 0`. Флаг `closed` ускоряет решение, но не
требуется: у запусков с `autoclose=false` он остаётся `false` навсегда. Такой критерий
защищает от «ready=true, а результаты ещё дописываются» — реального кейса тихой потери хвоста.
Дополнительно скан идёт с `--tail-check`.

Таймауты: `--timeout` (прогон, 3 ч по умолчанию), `--rerun-timeout` (реран, 2 ч); по их
истечении — код 6 и понятное сообщение.

## Core Rules

1. **Режим выбирается по запросу.** При неоднозначном входе (тип HF/QG/RM, команда, launch, rerun) — вопрос и остановка, не «похоже/наверное».
2. **Артефакты прогонов и эталоны — вне скилла:** прогоны в `~/.qa-artifacts` (переопределение: env `QA_ARTIFACTS_ROOT`, флаг `--root`), эталоны — кэш `~/.qa-artifacts/etalons` из ветки `qa-analysis-data`. Внутри скилла их не хранить и не коммитить.
3. **Пути резолвит `scripts/_paths.py`:** `QA_HOME` = env `QA_HOME` → родитель папки `scripts/`. Абсолютные пути не зашивать.
4. **Confluence — опционально; Jenkins — только по подтверждению.** Публикация отчёта в Confluence не обязательна (достаточно чата + базы результатов). Запуск перезапусков в Jenkins — только после явного подтверждения пользователя; автопубликация и автозапуск запрещены.
5. **Состояние между режимами — только через `~/.qa-artifacts`** (`expected_set.json`, `rerun_diff.json`, `dispatch.json`), не через парсинг Confluence.
6. **Все скрипты лежат в одной `scripts/`** — они импортируют друг друга; разнос по папкам даёт `ModuleNotFoundError`.
7. **Ничего не запускать без токена `TESTOPS_TOKEN`.** Confluence — через MCP `atlassian` (токен в `opencode.json`). Нет доступа — стоп и сообщение пользователю.
8. **Только стандартная библиотека Python.** Внешние зависимости не ставить.
9. **Числа, таблицы и @-список генерирует `render_markdown.py`**; переписывать их вручную в MCP-вызове запрещено.
10. **Эталон — единственный источник истины** о принадлежности теста команде; поле `Team` из TestOps — дополнительный сторож (двойной фильтр). Эталон читается из кэша `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt`, кэш скачивает `fetch_etalons.py` из ветки `qa-analysis-data` (`AUTOTEST/sfa`, `etalons/`).
11. **Контракты артефактов машиночитаемы.** Схемы — `config/contracts/*.schema.json`, проверка — `doctor.py`. Состояние между режимами — один файл `case_meta.json` (секции `run` / `dispatch` / `rerun`), второй не создавать.
12. **Эталоны не правятся руками и не коммитятся в скилл.** Изменения состава тестов — `update_etalon.py` в кэше, затем PR в ветку `qa-analysis-data`; после мержа операторы делают `fetch_etalons.py --refresh`.
13. **База результатов пополняется только подтверждёнными разборами.** `publish_results.py --push` — после рерана/глубокого разбора и подтверждения пользователя. Причины в базе — с evidence и статусом (`suspected`/`confirmed`/`refuted`); читать базу можно как гипотезы, но подтверждать заново.
14. **Чего-то нет на машине — предложи установить, а не обходи.** Если при выполнении обнаружилось, что нет компонента (git, Python 3.9+, токен, git-креды, ветка, кэш данных, MCP), скилл: (1) останавливается, не подменяя результат заглушкой; (2) определяет тип: самолечится скриптом (кэш данных, папки) — делает сразу; требует установки/настройки — предлагает конкретную команду под ОС и спрашивает разрешение; требует прав/доступа — говорит, какие шаги деградируют; (3) после согласия и установки повторяет проверку (`doctor.py`) и продолжает с того же шага. 🔴 Запрещено: молча пропускать шаг, подставлять пустые данные, выдавать «разбор» без скана, ставить пакеты/менять конфиг без явного согласия. Таблица «сигнал → чего нет → что предложить» — `references/toolkit-guide.md` (§ Окружение).
15. **Метрика — по НОМЕРАМ эталона, не по строкам запуска.** `counts` в `expected_set.json` агрегируют уникальные номера; серии Examples дают несколько строк на один номер. Считать «passed / все строки запуска» — грубая ошибка: реальный кейс 1334823 дал 48/91 = 52.7% вместо 14/53 = 26.4%. Числа брать только из `expected_set.json` / `scan_manifest.json`.
15a. **🔴 ПОЛНОТА ОХВАТА — главный вывод отчёта, а не сноска.** `scan_manifest.json` содержит
`etalon_covered`/`etalon_total`/`etalon_coverage_etalon_pct` (**сколько ЭТАЛОНА прогнано**) и
`etalon_missing_numbers` (**что не запускалось**). Если `etalon_missing_count > 0`:
   - **блок «⚠️ Прогон НЕПОЛНЫЙ» идёт ПЕРВЫМ в отчёте** — до статистики PASS/FAIL, отдельным
     абзацем с числом «N из M тестов не участвовали» и процентом покрытия (`render_markdown.py`
     ставит его автоматически; если отчёт пишется руками — порядок обязателен);
   - в отчёте **отдельной строкой** показывать «не запускалось: N», а не растворяться в % PASS;
   - **запрещено** утверждать «всё остальное проходит» / «дефектов нет» — про эти тесты данных нет;
   - если задача — «перезапустить ВСЕ тесты команды», их надо добавить в @-список
     (`dispatch_team_reruns.py --include-missing`), а не ограничиваться упавшими;
   - если покрытие < 95% при задаче «разобрать прогон целиком» — сообщить пользователю, что
     прогон неполный **в первой фразе ответа**, а не в конце.
   ⚠️ Не путать с `etalon_coverage_pct` (доля ЗАПУСКА, объяснённая эталоном): эта величина в норме
   близка к 100% и **не является** индикатором полноты. Реальный кейс: launch 1344527 — 152 из 282
   теста TX-T9 (53.9%), при этом скан печатал «100% запуска»; 130 тестов молча выпали из перезапуска.

15a-бис. **🔴 ДИАГНОЗ ПРОПУСКА (почему тест не запускался) — обязателен при `etalon_missing_count > 0`.**
Факт «не запускался» без причины бесполезен: от неё зависит, перезапускать или чинить. Скрипт
`diagnose_skips.py --launch-id {id} [--team {TEAM}]` пишет `launches/{id}/{team}/skip_diagnosis.json`
и печатает таблицу «Причина | Тестов | Что делать». Слои:
   - **A. своя сборка** — `jobRun` своего запуска (`GET /api/testresult/{id}` → `jobRun.externalId`),
     далее Jenkins API `/job/<path>/<n>/api/json`: `result` (`ABORTED`/`FAILURE`), наличие `Aborted by`
     в `consoleText`, переданные параметры `tags`. Сборки нет в Jenkins (ротация логов) → честно
     «не проверить», а не «tags не передавались»;
   - **B. свой репозиторий автотестов** — `git ls-tree -r` ветки `master` (`AUTOTEST/sfa`), поиск
     `<номер>.feature`; путь содержит `features/excluded/` → тест отключён и **перезапуск его не
     подхватит никогда** (нужно вернуть файл в `features/Tests` или убрать тест из эталона).
   Закрытый список исходов: `сборка прервана` / `сборка упала до этих тестов` / `теги не передавались` /
   `тест отключён в репозитории` / `нет файла с таким номером` / `тег передан, но сценарий не стартовал` /
   `не установлено: feature есть, статус сборки недоступен` / `неизвестно`. **Запрещено** подменять
   неустановленную причину догадкой — она печатается как «не установлено» с пометкой, что нужна ручная проверка.
   ⚠️ Отсутствие `<номер>.feature` НЕ доказывает отсутствие теста: номер может жить тегом внутри
   чужого `.feature` — поэтому это ориентир, а не диагноз.

15a-тер. **🔴 Сверка с ДРУГИМИ запусками — только с явного разрешения пользователя.** Соседние
launch'ы той же джобы (`QG_TX_T9_No_Parallel` vs общий `QG`), параллельные запуски поставки и любые
другие прогоны **не читаются автоматически** — ни для полноты, ни для «где же эти тесты». Это отдельное
решение оператора. Разрешено без спроса: своя сборка (`jobRun` своего запуска) и свой репозиторий автотестов.
15b. **🔴 Тесты команды ВНЕ эталона, но упавшие в прогоне — в @-список.** `new_tests` в
`expected_set.json` — это тесты `Team ∈ teams` с номером ∉ etalon. Если такой тест НЕ PASS, он
**обязан** попасть в перезапуск (иначе падение теряется). Автоматически добавлять его в файл
эталона по-прежнему нельзя (решение человека, `update_etalon.py`), но в @-список перезапуска —
обязательно. Реальный кейс: `39.02.03.07` упал с `Net::ReadTimeout` и не перезапускался.
16. **Скан сертифицирован — доверяй только ему.** `scan_testops.py` пишет в `scan_manifest.json` хеши `expected_set_sha256`, `nonpass_results_sha256` и `etalon_sha256`. Снимок без манифеста, с `complete != true`, `tail_mismatch == true` или с расхождением хеша **не используется**: `dispatch_team_reruns.py` и `classify_rerun.py` отказываются с ним работать (fail-loud). Это заменяет ручную «проверку глазами» — поэтому пересканировать, а не править `expected_set.json` руками.
17. **Пломба эталона.** `fetch_etalons.py` кладёт рядом с эталоном `<etalon>.sha256`; `scan_testops.py` сверяет и падает при расхождении. Правка эталона в кэше — только через `update_etalon.py` и PR в `qa-analysis-data`, не редактированием файла.
