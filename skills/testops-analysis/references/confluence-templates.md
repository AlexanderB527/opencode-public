# Публикация в Confluence через MCP (без скрипта)

> **Публикация в Confluence — ОПЦИОНАЛЬНА.** Основной результат разбора теперь живёт
> в базе `results/` (ветка `qa-analysis-data`, пишет `publish_results.py`), а отчёт
> можно отдать в чат. Страница нужна, когда её просят люди (руководитель, команда,
> ссылка в письме). Гейты ниже действуют, если публикуем.

> Часть скилла `testops-analysis`. Общие правила — `../SKILL.md`.
> Этот файл — конечная точка: обратных ссылок на режимы не содержит.

Скриптовой публикации больше нет: сетевой скрипт и HTML-генераторы удалены — их
дублировал MCP. Разметку страниц генерирует `scripts/render_markdown.py`
(детерминированно, числа считает Python), а в Confluence её вставляет агент через
MCP `atlassian`. Отдельная переменная с токеном публикации скриптам не нужна —
токен лежит в `opencode.json` для MCP.

## 1. Страница разбора запуска

Источник — `expected_set.json` (`launches/{launch_id}/{team}/expected_set.json`).

```powershell
py -X utf8 <QA_HOME>\scripts\render_markdown.py `
   --expected-set "~/.qa-artifacts/launches/{launch_id}/{team}/expected_set.json" `
   --out "<QA_HOME>/temp/page-analysis.md"
```

Секции (порядок и числа — строго из JSON, не переписывать):

| Секция | Содержимое |
|---|---|
| `# Анализ прогона {launch_name}` | заголовок из `launch_name` |
| `## Статистика` | Всего / Прошло / Упало / Сломано / Пропущено / Процент прохождения из `counts` |
| `## @-список (N)` | не-PASS номера с `@` в одну строку, N = `counts.nonpass` (уникальные номера) |
| `## Затронутые области (по классу ошибки)` | `Ошибка \| Тестов \| Результатов \| Теги` — сгруппированная таблица §7.2A |
| `## Статистика по командам` | из `teams_stats` или разбивки по `origin`; нет данных — секции нет |
| `## Новые тесты (вне эталона)` | из `expected_set.new_tests`; нет данных — секции нет |
| `## Детально по тестам` | `Номер \| Статус \| Класс ошибки \| Сообщение (кратко)` — справочно, для разбора |

> **«Тестов» vs «Результатов».** Параметризованные Examples дают несколько
> результатов на один номер. «Тестов» = уникальные номера (= длина @-списка),
> «Результатов» = строк результатов (совпадает с `manifest.nonpass_results`).
> Раньше оба числа назывались «Кол-во», и 39 против 42 читались как ошибка расчёта.

**Правило:** текст секций = вывод `render_markdown.py --expected-set`. Вставлять как есть:

- новая страница — `atlassian_confluence_create_page`
  (`space_key: SFAONPEGA`, `title: "Анализ прогона {launch.name}"`,
  `parent_id: 3703816519` — «Разбор прогона с помощью AI», `content_format: markdown`);
- существующая страница — `atlassian_confluence_update_page_section` по нужному заголовку.

Не пересчитывать числа вручную и не «причёсывать» таблицы в MCP-вызове.

## 2. Страница перезапуска

Источники — `rerun_diff.json` (обязательно) и `rerun_classification.json` (желательно).

```powershell
py -X utf8 <QA_HOME>\scripts\render_markdown.py `
   --rerun-diff "~/.qa-artifacts/reruns/{rerun_id}/rerun_diff.json" `
   --classification "~/.qa-artifacts/reruns/{rerun_id}/rerun_classification.json" `
   --out "<QA_HOME>/temp/page-rerun.md"
```

Секции:

| Секция | Содержимое |
|---|---|
| `# Перезапуск {rerun_id} относительно {expected_id}` | заголовок (+ команды из `teams`) |
| `## Итог` | `healed` / `failed_again` / `skipped` / `absent` из `stats` |
| `## Сводка по типам` | дефекты / автотест / система / триаж: кол-во и доля; покрытие evidence и стабильность |
| `## Снова упавшие по кластерам` | `Кластер \| Тестов \| Тип \| Confidence \| (Стабильно) \| Рекомендация` (из `clusters`, иначе `groups`/`items`) |
| `### 🔴/🟡/⚪/❓ …` | блоки кластеров по типу: стабильность, Диагноз/Обоснование/Шаги/Файлы, Confidence, Рекомендация, Тесты, подгруппы по локатору |
| `## Таблица по тестам` | `Номер \| Статус \| Класс ошибки \| Тип \| Confidence \| Кластер \| Вердикт \| Рекомендация` (только `items`, N = `counts.failed_again`) |
| `## Вылечившиеся (PASS)` | номера `healed` со статусом `PASS` |
| `## Новый @-список` | номера снова упавших в одну строку |

Секции без данных не выводятся — пустые таблицы и нули не выдумывать.

Тот же markdown печатает `classify_rerun.py --chat` (общий рендерер
`render_markdown.render_classification`) — отдельной разметки в чате нет.

Публикация: дочерняя страница «Разбор рерана …» под страницей анализа
(`page1_id`), через `atlassian_confluence_create_page` / `update_page_section`.

## 3. Гейты перед публикацией

Публикация блокируется, пока не выполнены ВСЕ пункты:

1. Длина @-списка = число не-PASS номеров (`counts.nonpass`). `render_markdown.py`
   сам падает с exit 1 при расхождении — это и есть гейт.
2. Объединение тегов сгруппированной таблицы = @-список (множественное равенство).
3. Сумма «Тестов» в группах = число не-PASS номеров.
4. Число строк «Детально по тестам» = число не-PASS номеров.
5. Скан полный (`scan_manifest.json`: `complete == true`, `tail_mismatch == false`).
6. Сверка `verify_sets.py` = `ЧИСТО` либо расхождение объяснено пользователю.
7. Пользователь **явно подтвердил** публикацию (авто-публикация запрещена). Если публикация
   не запрошена — гейты всё равно проверяются при записи в базу (`publish_results.py`):
   `complete == true`, схема `run_result.schema.json`, сходимость цифр.

## 4. Обновление существующей страницы

- `page_id` берётся из `~/.qa-artifacts/launches/{launch_id}/{team}/case_meta.json`
  (секции `run.page1_id` / `rerun.page2_id`); если записи нет или она от чужого прогона —
  спросить пользователя, не угадывать.
- При обновлении правится **только нужная секция** через
  `atlassian_confluence_update_page_section`; страница не пересоздаётся.
- Родителя с эталоном (3703816519) и страницу анализа не перезаписывать.

## 5. Пометка вылечившихся

На странице перезапуска:

- `healed` → статус `PASS` (тест прошёл в перезапуске);
- `failed_again` → статус **НЕ меняется** (FAIL остаётся FAIL, BROKEN остаётся BROKEN);
- `absent` / `skipped` → не участвовал, статус не трогаем.

`render_markdown.py` проставляет `PASS` для `healed` в отдельной секции
«Вылечившиеся (PASS)»; в «Таблице по тестам» остаются только снова упавшие
(их число = `counts.failed_again`).

## 6. Токены

- Отдельная переменная с токеном публикации скриптам больше **не нужна** — она нигде
  не читается (ни в `scripts/`, ни в `config/`).
- Доступ к Confluence — через MCP `atlassian`; токен MCP
  (`CONFLUENCE_PERSONAL_TOKEN`) прописан в `opencode.json` и уже входит в пресет.
- `TESTOPS_TOKEN` остаётся только для чтения TestOps API.

# Приложение: канон формата Страницы 1 (перенесено из режима разбора запуска)

> Канонические правила формата Страницы 1:
> сгруппированная таблица, @-список для Jenkins, запрет секции «Системные падения»,
> параметры публикации и верификация CP3.

КРИТИЧНО: публикацию выполняет ТОЛЬКО основной агент. Запрет `confluence_update_page` на страницу-родителя (confluence_page_id). Обновление существующей страницы анализа — только с явного подтверждения пользователя.

### 7.1. Единая публикация: полный контент в памяти → CP2 → опубликовать → CP3. Максимум 2 версии страницы; промежуточные публикации запрещены.

### 7.2. Стратегия: **1 страница** (Страница 1 — Основная). Страница 2 (разбор прогона) после первичного запуска НЕ создаётся — детальный разбор выполняется только на фазе rerun (режим классификации перезапуска).

**Страница 1 — Основная** (дочерняя под confluence_page_id = 3703816519 «Разбор прогона с помощью AI»; эта папка = Архив прошлых разборов):
- Заголовок: «Анализ прогона {launch.name}»
- Строка «Запуск: {launch.name} {team_display_name} {ссылка на запуск}»
- Статистика таблицей по командам (см. §6.1)
- **@-список для перепрогона (Jenkins)** (см. §7.2B): плоский список не-PASS номеров через пробел с `@`, отдельным блоком
- **Сгруппированная таблица ошибок** «Ошибка | Кол-во | Теги» (см. §7.2A): ВСЕ не-PASS тесты по классам причины. Отдельная секция «Системные падения» НЕ создаётся (§7.2C).
- Без ссылки на Страницу 2 (её нет)

#### A. Сгруппированная таблица ошибок на Странице 1 [ОБЯЗАТЕЛЬНЫЙ ФОРМАТ ВЫВОДА]
Заменить прежние отдельные блоки («🔴 FAIL-результаты» нумерованным списком, «🟡 Группировка BROKEN», «Системные падения») на ОДНУ сгруппированную по типу ошибки таблицу со ВСЕМИ не-PASS тестами.

Формат таблицы (одна строка = один класс ОШИБКИ, а не тест):
```
| Ошибка | Кол-во | Теги |
|--------|:------:|------|
| Элемент не найден (Unable to find visible xpath) | 61 | @02.11.01.02 @02.21 @02.87 ... |
| Failed to open TCP connection (sfa-at-linux-1:4444) | 28 | @02.11.01.01 @07.14.01 ... |
| ... | ... | ... |
```

Правила:
1. **Группировка по классу ошибки** (см. §5), НЕ по каждому тесту и НЕ по уникальному xpath. Несколько тестов с одинаковой причиной → одна строка. Классификатор группирует по паттерну §5, нормализуя конкретные параметры (xpath/хост:порт/даты) до класса.
2. **«Ошибка»** — название класса причины (первое совпадение §5), для сетевых — `Failed to open TCP connection (хост:порт)`, для ненайденного элемента — `Элемент не найден (Unable to find visible xpath)` и т.п.
3. **«Кол-во»** — ЧИСЛО не-PASS результатов в этой группе (ТОЧНОЕ, без «~»). Показывает импакт: чем больше — тем приоритетнее.
4. **«Теги»** — номера тестов с префиксом `@`, через пробел, ЕСТЕСТВЕННАЯ сортировка по числовым компонентам, каждый номер РОВНО 1 раз. Формат `@` единый с @-списком (для копирования в Jenkins).
5. **Полнота**: объединение тегов ВСЕХ строк == множество не-PASS номеров (@-список, §7.2B) == K; сумма «Кол-во» == not_passed_results. Каждый не-PASS результат учтён ровно в одной группе. Расхождение — БЛОК.
6. Сортировка строк таблицы — по убыванию «Кол-во» (импакт сначала), при равенстве — по алфавиту класса.
7. Таблицу на Странице 1 использовать как данные для обратного чтения (футурный rerun): формат строгий и парсится.
8. Конкретный текст ошибки (message/xpath) НЕ выводится в таблицу — он в артефакте `nonpass_results.jsonl` / `expected_set.json` (для rerun-классификации).

#### B. @-список для перепрогона (Jenkins) на Странице 1
После единой таблицы (§7.2A) выводить отдельным блоком плоский @-список всех не-PASS номеров — готовый к вставке в Jenkins как ОДИН параметр.

Формат блока:
```
### @-Список для перепрогона (Jenkins)
@10.02.01 @10.02.04 @10.02.05 ... (все не-PASS, через пробел, каждый РОВНО 1 раз, по возрастанию)
```

Правила:
1. **Содержимое** — все не-PASS номера (FAIL + BROKEN + SKIP), через пробел, с префиксом `@`, каждый РОВНО 1 раз (дедуп).
2. **Сортировка** — ЕСТЕСТВЕННАЯ по возрастанию (как в таблице §7.2A и п.6.5): 02.x → 10.x → 39.x.
3. **Источник** — тот же набор, что в п.6.5. len(@-список) == K.
4. Блок вставлять **после секции статистики**, перед сгруппированной таблицей (§7.2A). Это отдельный артефакт для копирования в Jenkins-параметр; таблица §7.2A остаётся без изменений (порядок блоков на Стр.1: Статистика → @-список → Сгруппированная таблица).
5. **Полнота:** @-список должен содержать те же номера, что и объединение тегов таблицы §7.2A (множественное равенство). Расхождение — БЛОК/пересмотр. len(@-список) == K.

**Разбор прогона НЕ создаётся после первичного запуска.** Страница 2 отсутствует в этой схеме. Полный детальный разбор причин (по типам ошибок, с рекомендациями) выполняется ТОЛЬКО на фазе rerun — режим классификации перезапуска (он же публикует разбор по повторно упавшим). Первичный запуск отдаёт: Страницу 1 (per-team статистика + @-список + сгруппированная таблица ошибок §7.2A).

#### C. Системные/инфраструктурные падения — НЕ отдельная секция на Странице 1.
Ранее системные (окружение/TCP-таймауты) выносились в собственную секцию. По решению рецензента отдельная секция **убрана**: инфраструктурные падения видны **как обычные группы** сгруппированной таблицы §7.2A (например `Failed to open TCP connection (sfa-at-linux-1:4444)`), с их «Кол-во» и тегами — импакт и так читается. НЕ создавать блок «🔴 Системные падения». Определение системного падения (для группировки §5): `Failed to open TCP connection`, `execution expired`, `Net::ReadTimeout`, `Connection timed out`, `Connection refused`, `socket`, `sfa-at-linux-1:4444`, `jenkins.*:80`, 500 от среды. Они просто группируются в §7.2A как обычные классы.

#### D. Архив прошлых разборов (источник истории причин по номеру теста)
Дочерние страницы корня `confluence_page_id = 3703816519` («Разбор прогона с помощью AI») образуют **Архив** прошлых «Анализ прогона …». Каждая такая страница — разбор конкретного запуска.

Анализ повторяемости (по номеру теста) читает ТОЛЬКО этот Архив (папку 3703816519), вычитывает таблицы §7.2A прошлых прогонов и по номеру теста строит историю причин/статусов. Это единственное место, откуда берётся история — НЕ парсить другие папки/пространства. На свежей установке (первый запуск) Архив может быть пуст/мал — тогда повторяемость недоступна до накопления истории.

### 7.9. **Контракт handoff → режим классификации перезапуска (фаза rerun).**
После публикации Страницы 1 (CP3) режим разбора запуска завершает первичный разбор. Детальный разбор причин выполняет режим классификации перезапуска. Передаваемые артефакты (в `~/.qa-artifacts/`):
- `launches/{launch_id}/{team}/expected_set.json` — полная картина номеров команды со статусами и `pass_rate`;
- `launches/{launch_id}/{team}/nonpass_results.jsonl` — не-PASS результаты (для классификации);
- `launches/{launch_id}/{team}/at_list.txt` — @-список первичного запуска;

Режим классификации перезапуска публикует Страницу 2 (разбор по типам) сам; режим разбора запуска Страницу 2 НЕ создаёт.
