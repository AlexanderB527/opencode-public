# Как пользоваться скиллом testops-analysis и что ожидать

> Часть скилла `testops-analysis`. Это **пользовательская инструкция** — как запустить,
> что скилл спросит, что сделает и какие файлы/страницы появятся. Режимы и пошаговые
> скрипты — в `run-analysis.md`, `dispatch.md`, `rerun-classifier.md`, `deep-failure.md`;
> справочник путей и скриптов — `toolkit-guide.md`.

---

## 1. Как вызвать

Скилл подключён пресетом `qa-skillmate` (primary-агент **«QA SkillMate»**). Отдельной
slash-команды у него нет — он **активируется по смыслу фразы** (описание SKILL.md).

**Триггеры (что писать в чат):**

| Хочешь | Пиши примерно |
|---|---|
| Разобрать прогон | «разбери упавшие», «анализ прогона», «посмотри что упало», ссылка на `…/launch/{id}` + команда + тип HF/QG/RM |
| Раздать перезапуск | «раздай упавших по командам», «перезапусти командные джобы» |
| Классифицировать реран | «разбор рерана», «классифицируй реран 1240000 относительно 1234567», «отдели ошибки системы от дефектов» |
| Причина конкретного теста | «почему упал @10.05.03.01 и что чинить», «глубоко разбери @02.01.07 @10.02.04» |
| Слить два запуска | «объедини запуски 1334823 и 1363174» (утилита `merge_launches.py`) |

**Когда НЕ сработает (и не должен):** «напиши новые тест-кейсы», «сделай UI-сценарий»,
«обнови документацию» — это не разбор падений, скилл не берётся.

## 2. Что скилл спросит ДО работы (не угадывает)

Если во входе не хватает однозначности — задаёт **батчем** (до 4 вопросов) и **останавливается**:

- **тип тестов** — HF / QG / RM (если не читается из `launch.name`);
- **команду(ы)** — `T9`, `TX`, `T9,TX`… (имя папки эталона `TX-T9` ≠ имя команды в TestOps);
- **тег тестировщика** — если разбор «по моим тестам» (логин `u_xxxx` ≠ тег в TestOps);
- для рерана — **ID первичного запуска** и **ID rerun-запуска**, для глубокого разбора — **какой набор тестов**.

Это не каприз: эталон строится от команды и типа, неверный вход = неверный скан.

## 3. Что ожидать: по режимам

### 3.1 Разбор запуска (главный вход)

Вход: `launch_id` + команда + тип.

Что делает и что вернёт:
1. `doctor.py` — проверка окружения; при `ОШИБКА` — остановка и предложение настройки.
2. `fetch_etalons.py` (если кэш пуст) — скачивает эталон команды.
3. `scan_testops.py` — скан TestOps (пагинация, двойной фильтр, гейт хвоста) →
   пишет в `~/.qa-artifacts/launches/{id}/{team}/`:
   `expected_set.json` (статистика по номерам), `nonpass_results.jsonl`, `scan_manifest.json` (сертификат полноты).
4. `verify_sets.py` — сверка @-списка с эталоном → обязательное **«ЧИСТО»**.
5. `render_markdown.py` — готовая markdown-страница (числа считает Python, не «в голове»).
6. `publish_results.py --push` — база знаний (по подтверждению).

**Что вы увидите в чате:** таблицу статистики (Всего/Прошло/Упало/Сломано/Пропущено/%),
@-список, сгруппированную таблицу ошибок, разбивку по командам, список новых тестов вне эталона.
**Что спросит дальше:** публиковать ли в Confluence, раздавать ли перезапуск, что делать с новыми тестами.

### 3.2 Раздача перезапусков

Вход: `launch_id` со сделанным сканом.

1. `dispatch_team_reruns.py --dry-run` — план (кто куда, сколько тестов), **ничего не запускает**.
2. После подтверждения — боевой запуск: Jenkins `DEBUG/<TEAM>` с `parallel=15`, `rerun=1`.
3. Результат — `dispatch.json` + ссылки на сборки + страница «AI run …».

**Чего ждать:** команды с пустым @-списком не запускаются (`skipped_empty` — норма);
`unmapped`/`duplicate_scan` — решение человека. Запуск — только по явному «запускай».

### 3.3 Классификация перезапуска

Вход: `rerun_id` + `первичный launch_id`.

1. `diff_rerun.py` → `rerun_diff.json` (healed / failed_again / skipped / absent).
2. `classify_rerun.py --chat` → вердикт в чат по кластерам: **дефект / автотест / система / триаж**.
3. Публикация в Confluence — только по «публикуй»; результат в чат — всегда.

**Чего ждать:** статус снова-упавших НЕ меняется, вылечившиеся → `PASS`; BROKEN разбирается
так же, как FAIL (не «упали с теми же ошибками»); low-confidence → триаж, не выдаётся за факт.

### 3.4 Глубокий разбор

Вход: список тестов / launch.

**Чего ждать:** на каждый тест блок «Причина + Решение» с локусом `файл:строка`/Confluence-ссылкой;
если данных не хватает — честное «не подтверждено» + что запросить у человека. Режим read-only.

### 3.5 Слияние запусков

Вход: два launch id. `merge_launches.py --from A --to B` — сначала план, затем `--yes`.
Необратимо: источник A исчезает как отдельный запуск.

### 3.6 Планирование техдолга TX/T9

Вход: ничего или группа/уровень («самые простые TX», «что в TX-J»).

**Чего ждать:** ответ **из реестра** `references/techdebt-tx-t9.md`, без повторного
разбора xlsx и без обращения к TestOps. Реестр даёт раскладку 149 тестов техдолга
(TX 105 + T9 44) по уровням L1/L2/L3 и 22 паттерн-группам с якорями `TX-A…TX-P`,
`T9-A…T9-F`. Статусы и причины падений в реестре намеренно отсутствуют — они
берутся из исходной таблицы техдолга.

## 4. Сквозной пример (разбор → раздача → классификация)

```
> разбери упавшие в запуске 1334823, команды T9 и TX, тип RM
< (вопрос, если неясно) тип/команды
… scan_testops → verify_sets → render_markdown …
< Статистика: всего 53, прошло 14, упало 8, сломано 31 → 26.4%
< @-список (39): @01.10.04 @01.10.06.01 …
< Сгруппированная таблица ошибок
< Новые тесты вне эталона: @10.15.07.01 — добавить в эталон?

> раздай упавших по командам
< План: TX-T9 → DEBUG/TX-T9, 39 тестов
> запускай
< Сборка DEBUG/TX-T9 #8 → ссылка

… (джоба отработала, появился rerun-запуск 1363174) …

> классифицируй реран 1363174 относительно 1334823
< Снова упали: Z | Вылечились: Y | Не участвовали: U
< 🔴 Дефекты / 🟡 Автотест / ⚪ Системные / ❓ Триаж
< Новый @-список для следующего перезапуска
```

## 5. Где и что появляется на диске

| Что | Где |
|---|---|
| кэш эталонов | `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt` (+`.sha256`) |
| снимок прогона по команде | `~/.qa-artifacts/launches/{id}/{team}/expected_set.json`, `nonpass_results.jsonl`, `scan_manifest.json`, `at_list.txt`, `case_meta.json` |
| раздача | `~/.qa-artifacts/launches/{id}/dispatch.json` |
| дифф/классификация рерана | `~/.qa-artifacts/reruns/{rerun_id}/rerun_diff.json`, `rerun_classification.json` |
| журнал слияний | `~/.qa-artifacts/launches/{to}/merge.json` |
| база знаний | ветка `qa-analysis-data` (`results/<TEAM>/index.json`, `causes.jsonl`, `launches/*.json`) |

---

## 6. Границы и подтверждения (чего НЕ ждать)

- **Авто-публикаций и авто-запусков нет.** Confluence и Jenkins — только по явному подтверждению
  («публикуй» / «запускай»). Результат по умолчанию — в чат и в артефакты.
- **Слияние запусков не автоматическое** — `merge_launches.py` требует `--yes`.
- **Причины падений на первичном скане не ставятся** — только на фазе rerun/deep.
- **Эталон не правится на лету**: новые тесты — через `update_etalon.py` + PR, а не вручную.
- **Скилл не пишет код продукта и не меняет тесты** — он разбирает, не чинит.
