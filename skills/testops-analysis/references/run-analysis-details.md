> Часть скилла `testops-analysis`. Общие правила — `../SKILL.md`.

## 1. Входные данные

- Ссылка на запуск — URL вида https://example.invalid
- Тип тестов — определяется ИЗ `launch.name`: содержит "QG" → QG, "HF" → HF, иначе спросить. `launch.name` — первичный источник, а не fallback; спрашивать только если он не определяет тип.
- Команды — массив строк, НАПРИМЕР ["T9", "TX"]. **Обязательный вход.** Порядок = порядок вывода. Если не указан — спросить. Путь эталона строится от команд (см. п.2).

team_display_name: ["T9", "TX"] → "T9+TX", ["T9"] → "T9"

### Конфигурация

| Параметр | HF | QG | RM |
|----------|----|----|----|
| etalon_path | кэш `~/.qa-artifacts/etalons/<Команда>/etalon_HF.txt` | кэш `~/.qa-artifacts/etalons/<Команда>/etalon_QG.txt` | кэш `~/.qa-artifacts/etalons/<Команда>/etalon_RM.txt`, определяется по команде (С2) |
| confluence_page_id (родитель публикации) | 3703816519 («Разбор прогона с помощью AI») | 3703816519 («Разбор прогона с помощью AI») | 3703816519 («Разбор прогона с помощью AI») |
| space_key | SFAONPEGA | SFAONPEGA | SFAONPEGA |

> 📁 **Путь эталона:** локальная папка команды в кэше `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt`, где `<Команда>` — нормализованное имя (например T9/TX → `TX-T9`), `<тип>` — QG/HF/RM. Внутри папки — файлы по типам. Эталоны НЕ лежат в репозитории скилла: источник истины — ветка `qa-analysis-data` (`AUTOTEST/sfa`, `etalons/<TEAM>/etalon_<тип>.txt`), кэш скачивает `scripts/fetch_etalons.py`. Не зашит жёстко: если файла нет в кэше — `fetch_etalons.py --team <TEAM> --type <тип>`, затем выгрузка из прогона (fallback) или уточнение у пользователя.

### 🔴 Определение эталона (С2) — скилл определяет сам или уточняет

Эталон выбирается **исходя из запроса** и **команды**, НЕ зашит под T9/TX:
1. **Определить команду/команды** из запроса (например «разбор прогона T9», «команда TX», ссылка на launch с указанием команды). Если команда не задана явно или их несколько, а разбор нужен по одной — **спросить у пользователя**.
2. **Путь к эталону** строится от команды по структуре кэша: папка `~/.qa-artifacts/etalons/<Команда>/`, файл `etalon_<тип>.txt`. Для многословной команды использовать имя из `teams` (например T9/TX → папка `TX-T9`, файл `etalon_<тип>.txt`). Проверить существование файла локально (`read`/`glob`); нет — скачать `fetch_etalons.py --team <Команда> --type <тип>`.
3. **Если команда не T9/TX** (например «команда Az», «команда 18», «T12») — эталон соответствует ДРУГОЙ папке в ветке `qa-analysis-data`: `etalons/<TEAM>/etalon_<тип>.txt` (существование проверить `fetch_etalons.py --list`). Если файла нет ни в ветке, ни в кэше — **уточнить у пользователя** локальный путь либо создать эталон выгрузкой из прогона (аналогично `export_team_etalons.py`).
4. После загрузки — обязательный **контроль формата**: N > 0, номера по паттерну `^\d{2}(\.\d{2,3})+`, уникальны. Несовпадение → «Не тот файл эталона» → спросить пользователя. После скана — контроль пересечения с запуском (§2.2).

→ **С2**: эталон определяется самим скиллом из запроса (команда) или через уточнение у пользователя; НЕ зашит намертво.

## 2. Эталон — файл в кэше оператора (из ветки qa-analysis-data)

**Поля манифеста скана (не путать «результаты» и «номера»):**

| Поле | Смысл |
|---|---|
| `nonpass_results` | строк результатов (Examples учтены) = число строк `nonpass_results.jsonl` |
| `nonpass_numbers` | уникальных номеров = `counts.nonpass` = длина @-списка |
| `etalon_overlap` / `etalon_coverage_pct` | сколько номеров запуска объяснено эталоном (**доля запуска**) |
| `etalon_covered` / `etalon_total` / `etalon_coverage_etalon_pct` | 🔴 **сколько эталона реально прогнано** (доля эталона) — главный индикатор полноты |
| `etalon_missing_numbers` / `etalon_missing_count` | номера эталона, которых в прогоне НЕ было (не запускались) |
| `team_rows_without_number` | строки своей команды без распознанного номера (не сопоставимы с эталоном) |
| `new_test_numbers` / `new_test_count` | тесты команды вне эталона (дублируются в `expected_set.new_tests`) |

2.1. Чтение файла эталона: построить путь от команды по структуре кэша `~/.qa-artifacts/etalons/<Команда>/etalon_<тип>.txt` (для T9/TX — папка `TX-T9`, файл `etalon_<тип>.txt`), затем локальный `read` файла (или `glob` для обнаружения; нет файла — `fetch_etalons.py --team <Команда> --type <тип>`). Парсинг: из каждой строки извлечь номер паттерном `^\d{2}(\.\d{2,3})+` (в начале строки; номера бывают до 6 компонент: 39.02.04.01.01.01). Построить множество etalon_numbers (дедуп), запомнить N.

2.2. Контроль эталона (ОБЯЗАТЕЛЕН — ловит не тот файл):

**Уровень 1 — формат (до скана):** N > 0; номера соответствуют паттерну `^\d{2}(\.\d{2,3})+`;
файл не пуст; номера уникальны. Нарушение → «Не тот файл эталона» → спросить пользователя.

**Уровень 2 — пересечение с запуском (после скана, самое ценное):**
`etalon ∩ номера_запуска == 0` → **BLOCK**: «эталон не пересекается с запуском — вероятно,
неверный тип (HF/QG/RM) или команда». Это ловит реальную ошибку выбора эталона без всяких
конфигов: типы не пересекаются (RM ∩ QG = 0), поэтому неверный тип даёт ноль всегда.

**Уровень 3а — покрытие ЗАПУСКА (мягкий):** `etalon_coverage_pct` < 50 % → **WARN** «возможно, эталон
устарел». Дрейф эталона — норма (команды добавляют тесты), поэтому это предупреждение, а НЕ блок:
жёсткая фиксация `count` заваливала бы нормальные сканы после каждого добавления тестов.

**Уровень 3б — 🔴 покрытие ЭТАЛОНА (главный гейт полноты):** `etalon_coverage_etalon_pct` =
`etalon_covered / etalon_total`. Показывает, какая доля тестов команды **реально прогнана** в запуске.
`< 95 %` → скан остаётся валидным, но печатается «прогон неполный» + список `etalon_missing_numbers`.

> ⚠️ **Не путать два покрытия.** `etalon_coverage_pct` (доля запуска, объяснённая эталоном) — это
> контроль правильности эталона, величина «сколько наших тестов мы узнали». `etalon_coverage_etalon_pct`
> (доля эталона, попавшая в прогон) — контроль **полноты прогона**. Раньше второй метрики не было, а
> первый показатель считался от уже отфильтрованного множества и тем самым **всегда** давал 100%.
> Реальный кейс: launch 1344527 содержал 151 из 281 теста TX-T9 (53.7%), но скан показывал
> «etalon_overlap 100% запуска» — недостача 130 тестов была невидима и они не попали в перезапуск.

**Правило интерпретации:** если `etalon_missing_count > 0`, то про эти тесты **нельзя сказать
«прошли» или «упали»** — их не запускали. В отчёте это отдельная строка, а не часть % PASS.
Для задачи «перезапустить все тесты команды» недостающие номера добавляются в @-список через
`dispatch_team_reruns.py --include-missing`.

> Файла `sanity.json` в поставке нет: он дублировал число строк эталона, устаревал при
> любом дрейфе и не читался ни одним скриптом. Проверка пересечения покрывает его задачу.

2.3. Fallback: если в кэше файла эталона нет — сначала `fetch_etalons.py --team <Команда> --type <тип>` (сеть, нужен git-доступ к `AUTOTEST/sfa`). Если доступа/сети нет или команды нет в ветке — **уточнить локальный путь у пользователя** либо создать эталон выгрузкой из прогона (аналогично `export_team_etalons.py`, формат `номер Название`). Confluence как источник — ТОЛЬКО с явным подтверждением пользователя и пометкой в отчёте (риск ложных номеров чужих команд).

2.4. **Сохранение эталона в файл (ОБЯЗАТЕЛЬНО):** после загрузки и санити-контроля эталон должен лежать файлом в кэше `~/.qa-artifacts/etalons/<Команда>/etalon_<тип>.txt` (формат `номер Название`, по одному на строку; для T9/TX — папка `TX-T9`, файл `etalon_<тип>.txt`). Это даёт инструментальный источник для верификации (п.3.6) и скана (п.3.2), исключая повторную сверку «в голове». Если сохранение невозможно (нет ФС) — НЕ продолжать к верификации, сообщить пользователю.

→ CP1: Эталон загружен? N номеров? Санити-контроль пройден? Лежит файлом в кэше `~/.qa-artifacts/etalons/<Команда>/etalon_<тип>.txt`?

## 3. Загрузка TestOps — ТОЛЬКО через API + артефакт скана

ЗАПРЕЩЕНО: сохранять полный отчёт в файл и парсить его через grep/read_file — потеря данных на больших запусках. Все данные — из ответов API. Извлечённые не-PASS результаты записываются скриптом в **артефакт скана** (`nonpass_results.jsonl`, п.3.2); итоговый анализ строится по данным jsonl (по offset/limit), не по grep полного отчёта.

3.1. Дешёвые предпроверки:
- `testops_launch_get_statistic(launchId)` — счётчики (passed/failed/broken/skipped), progress.ready
- `testops_launch_get(launchId)` — launch.name

3.2. Постраничный скан — ЧЕРЕЗ `scan_testops.py`. ЗАПРЕЩЕНО итерировать `testops_launch_list_test_results` в контекст постранично: скрипт делает это сам.

Сгенерировать (если файла нет) и запустить:
```
python scan_testops.py --launch-id {launchId} --teams "{T9,TX}" --etalon "~/.qa-artifacts/etalons/<Команда>/etalon_<тип>.txt"
```
Скрипт: пагинация size=100 (size>100 молча обрезает — скрипт сам не даст), применяет двойной фильтр (п.3.3), сохраняет ТОЛЬКО не-PASS результаты в `~/.qa-artifacts/launches/{launchId}/{team}/nonpass_results.jsonl` и манифест `scan_manifest.json` (в той же папке команды). В stdout — только статистика и пути. 🔴 Скан всегда пишет в подпапку `{team}/`, чтобы не затереть expected_set другой команды того же запуска.

**3.2a. Режимы среза (читать `expected_set.json` окнами, БЕЗ повторного скана).**
Когда `expected_set.json` уже создан (тем же запуском ранее), НЕ запускать полный скан и НЕ читать полный дамп файла в контекст — использовать подрежимы среза (читать срез вместо файла целиком):
```
py -X utf8 scan_testops.py --launch-id {launchId} --teams "{T9,TX}" --summary   # одна строка counts
py -X utf8 scan_testops.py --launch-id {launchId} --teams "{T9,TX}" --nonpass   # «номер статус первая_причина» для failed/broken/skipped
py -X utf8 scan_testops.py --launch-id {launchId} --teams "{T9,TX}" --numbers   # только expected_numbers (по одному в строке)
```
Поиск файла: `launches/{launchId}/{team}/expected_set.json`, иначе `launches/{launchId}/expected_set.json`. `--nonpass` НЕ печатает `result_ids`/`count`/`statuses[]` — только компактный срез. Если файла нет — выполняется обычный скан (нужны `--etalon` и токен).

**3.2c. Per-team агрегат (флаг `--per-team`).**
Добавляет в `expected_set.json` секцию `teams_stats` — result-level счётчики по командам:
`{ "<TEAM>": {total, passed, failed, broken, skipped, uniq_nonpass} }` (команда нормализуется `normalize_team`). Инвариант: `Σ total по командам == число результатов команд после двойного фильтра`. Это единственный источник per-team статистики для публикации (§6.1 / §7.2A) — считает скрипт, а не LLM.

3.2b. **МАНИФЕСТ СКАНА (детерминированный гейт полноты — контекст не перегружаем)**
После скана прочитать `scan_manifest.json` и свериться ИНСТРУМЕНТАЛЬНО:
- `complete == true` (скрипт сверил `rows_scanned == total`; при расхождении он сам завершается с exit != 0).
- `nonpass_count` — сколько строк в jsonl (контрольное число для п.7.2A: строк таблицы == not_passed_results).

Расхождение/exit != 0 → БЛОК: пересканировать, НЕ продолжать. `complete == true` — обязательная строка в CP2.

Чтение `nonpass_results.jsonl` для анализа — ТОЛЬКО по offset/limit (окнами), детерминированно, не «прочитал весь и запомнил». Это уже разрешённая категория (§5, §7.6).

3.3. Двойной фильтр каждого результата (ОБА условия):

- УСЛОВИЕ 1: Team ∈ teams ПОСЛЕ НОРМАЛИЗАЦИИ. Значения в TestOps вида "SFA Команда ТX" / "SFA Команда T9" — буква может быть кириллической «Т» или латинской «T». Нормализация: убрать пробелы, заменить кириллические «Т»/«т» на латинские «T»/«t», затем сравнить с teams.
- УСЛОВИЕ 2: номер ∈ etalon_numbers.

| Team ∈ teams? | номер ∈ etalon? | Действие |
|:---:|:---:|:---|
| ДА | ДА | ВКЛЮЧИТЬ — тест нашей команды |
| ДА | НЕТ | ОТБРОСИТЬ; добавить в new_test_numbers (п.3.7), показать пользователю |
| НЕТ | ДА | ОТБРОСИТЬ — чужой тест (номер в эталоне, выполняется чужой командой) |
| НЕТ | НЕТ | ОТБРОСИТЬ — чужой тест |

Эталон авторитетнее поля Team: номер ∉ etalon = тест не нашей команды, даже если Team совпадает (исключение — подтверждённые пользователем новые тесты, п.3.7).

Для каждого включённого результата сохранить в `nonpass_results.jsonl` (это делает `scan_testops.py`): testcase_id, suite, status (FAIL/BROKEN/SKIP), team (нормализованная), result_id, parameter (Examples, если есть), message (поле результата).

3.4. Извлечение реального сообщения об ошибке (для FAIL/BROKEN):

Реальная причина падения — в ПОСЛЕДНЕМ УПАВШЕМ ШАГЕ. Приоритет:
1. Если ответ `testops_launch_list_test_results` содержит steps для результата — найти последний шаг со status failed/broken, взять его message.
2. Иначе — `testops_testcase_get_scenario(testcase_id)`: найти последний failed/broken шаг, взять message. ВНИМАНИЕ: для параметризованных Examples (несколько результатов на один testcase) шаги могут быть общими — в этом случае предпочесть поле message результата.
3. Иначе — поле message результата.
4. Пусто/отсутствует — группа «Без сообщения».

Для BROKEN-результатов: если их > 50 — сгруппировать по полю message результата (у broken оно обычно есть); пустые — точечно по шагам (как выше); если и там пусто — «Без сообщения».

ЗАПРЕЩЕНО: придумывать причину падения. Только из данных API.

3.5. Верификация фильтрации (обязательно):
- Собрать уникальные Team у включённых результатов; если найдено Team ∉ teams — УДАЛИТЬ эти результаты, пересчитать статистику, вывести «Отброшено {count} результатов с Team ∉ teams: {список_Team}».
- Собрать уникальные номера из failed_list → failed_numbers; каждый номер ∈ etalon? Нет → ИСКЛЮЧИТЬ, пересчитать статистику, вывести «Исключено {count} номеров, не входящих в эталон: {номера}».

3.6. ПРОГРАММНАЯ ВЕРИФИКАЦИЯ @-списка по эталону (ОБЯЗАТЕЛЬНА; инструментальная + числовой вывод; выполняется после п.6.5 и до публикации):

ЭТО ИНСТРУМЕНТАЛЬНАЯ ПРОВЕРКА, А НЕ РАСЧЁТ "В ГОЛОВЕ". Запрещено отмечать её выполнение, отметив чекбокс CP2 или написав «верифицировано» — ОКРУЖЕНИЕ ДОЛЖНО ПОСЧИТАТЬ, а не модель. Выполнять план ниже в заявленном порядке; если tool-вызов возвращает сбой/пустоту — НЕ интерпретировать как «чисто», а повторить или остановиться (см. шаг 5).

1. **Подготовка файлов (ОБЯЗАТЕЛЬНО):** записать в `~/.qa-artifacts/launches/{launch_id}/{team}/at_list.txt` @-список (по одному номеру на строку). Эталон уже лежит в кэше `~/.qa-artifacts/etalons/<Команда>/etalon_<тип>.txt` (п.2.4). Оба файла — обязательный объективный след; БЕЗ них инструментальная сверка невозможна.
2. **Инструментальная сверка — ЧЕРЕЗ `verify_sets.py`:** запустить
   `python verify_sets.py --at-list "~/.qa-artifacts/launches/{launch_id}/{team}/at_list.txt" --etalon "~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt"`
   Скрипт читает оба файла, считает `set(at_list) − set(etalon)` и печатает вердикт `ЧИСТО` (exit 0) или `ЕСТЬ ЛИШНИЕ` (exit 1). НЕ полагаться на «помню, что это есть» и НЕ сверять «по числам из контекста п.2» — только через скрипт по файлам.
3. **Исключение чужих:** каждый номер, для которого сверка дала `∉ etalon` И он не подтверждён пользователем (п.3.7), → УДАЛИТЬ из @-списка и ВСЕХ таблиц, пересчитать статистику.
4. **Обязательный числовой вывод [принудительная строка]: вывести в чат РОВНО такой блок, подставив числа:**
   ```
   ВЕРИФИКАЦИЯ @-СПИСКА:
   - Номеров в @-списке: {K}
   - Из них ∈ etalon: {M}
   - Из них ∉ etalon: {K-M} → {номера через пробел}
   - Вывод: {K-M == 0 ? 'ЧИСТО' : 'ЕСТЬ ЛИШНИЕ — публикация ЗАБЛОКИРОВАНА'}
   ```
   Строка обязательна. Если `K-M > 0` → публикация ЗАБЛОКИРОВАНА: удалить лишние, пересчитать статистику, ПОВТОРИТЬ шаги 2–4. Только после «ЧИСТО» — переход к публикации (ФАЗА 2).
5. **Останов при сбое:** если любой tool-вызов шага 2 вернул ошибку/пустоту (файл не найден, grep без вывода и т.п.) — это НЕ «чисто». Повторить вызов один раз; при повторном сбое — остановиться и сообщить пользователю, НЕ публиковать и не выдавать «ЧИСТО».
6. **Начальная итерация строгая:** сверка выполняется на ТЕКУЩЕМ @-списке (после п.6.5), включая его фактическое содержимое, а не «верифицирую то, что верифицировал раньше». Если при повторных итерациях чужих не осталось — финальная строка блока обязана отражать ФАКТИЧЕСКИЙ @-список, который реально уходит в публикацию (совпадает с п.6.5 после исключений).

**Дополнительная страховка (независимость):** т.к. проверка `номер ∈ etalon` — чистая механика, и скилл запрещает доверять единственному «мне кажется», при сомнении допустимо (но не обязательно) продублировать сверку по `nonpass_results.jsonl` и по эталону через `verify_sets.py`, сравнив результат с «в голове». Это добавляет независимый источник, но ключевой механизм — обязательная строка-вердикт выше.

3.7. Новые тесты: `new_test_numbers` берутся из `scan_manifest.json` (скрипт `scan_testops.py` собирает их автоматически: Team ∈ teams, номер ∉ etalon, ЛЮБОЙ статус). Показать пользователю таблицу «Номер | Название | Team | Статусы» и запросить подтверждение (да/нет/выборочно). До подтверждения новые тесты в текущий @-список и таблицы НЕ включаются. Подтверждённые — обрабатываются по §3.9 (автоподдержка эталона).

3.8. ГЕЙТ ХВОСТА (ОБЯЗАТЕЛЕН — ловит тихую потерю данных):
Запустить `scan_testops.py` с флагом `--tail-check`: скрипт повторно запрашивает последние min(6, pages) страниц (size=100) и сверяет `result_id` записанных не-PASS результатов. В манифесте: `tail_checked: true`; `tail_mismatch: true` (или exit != 0) → пересканировать затронутый диапазон страниц. Без прохождения гейта — публикация ЗАБЛОКИРОВАНА.

→ CP2 (скан): эталон загружен и санити-проверен? Пагинация полная? complete == true (манифест скана)? Гейт хвоста пройден? Двойной фильтр и верификация по эталону выполнены?

3.9. **Автоподдержка эталона (самоподдерживающийся эталон — без ручного труда).**
Эталон НЕ ведётся вручную: он бутстрапится один раз и дальше дополняется автоматически по подтверждению пользователя.

1. **Бутстрап (разово):** сначала пробуем взять эталон из ветки — `python fetch_etalons.py --team <TEAM> --type <тип>`. Если команды нет в ветке или файл пуст (N=0) — сгенерировать из доверенного прогона: `python export_team_etalons.py --launch-id {id} --type {тип}` (пишет в кэш `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt`). Далее — санити-контроль §2.2 и PR в ветку `qa-analysis-data`. Уже сгенерированный файл НЕ перегенерировать.
2. **Каждый прогон:** `scan_testops.py` пишет `new_test_numbers` в `scan_manifest.json` (детекция новых тестов команды, §3.7).
3. **Показ кандидатов:** таблица из §3.7 → `question` (да/нет/выборочно).
4. **Применение (ТОЛЬКО после подтверждения):** `python update_etalon.py --etalon "<путь etalon_<тип>.txt>" --input "<json new_test_numbers>"` — скрипт дописывает подтверждённые номера в формате `номер Название`, делает естественную сортировку и дедуп, создаёт `.bak`-копию перед записью. Запрещено дописывать эталон вручную (edit/write по файлу) — только через скрипт.
5. **Повторная сверка:** `verify_sets.py` (эталон и @-список консистентны). Если в запуске появились номера вне эталона — это новые тесты команды: показать их пользователю и по подтверждению дописать в эталон через `update_etalon.py` (фиксированного `count` нет — эталон живёт и меняется).
6. **Перенос в ветку:** правка кэша действует только у этого оператора. Подтверждённое изменение — PR в ветку `qa-analysis-data` (файл `etalons/<TEAM>/etalon_<тип>.txt` целиком); после мержа остальные делают `fetch_etalons.py --refresh`.

Инварианты:
- Без подтверждения пользователя эталон НЕ меняется.
- `update_etalon.py` идемпотентен (повторный запуск с теми же номерами = без изменений).
- Источник новых тестов — ТОЛЬКО скан TestOps (`new_test_numbers`); repo-grep AUTOTEST НЕ используется.

## 4. Контроль полноты

- found_in_launch = все найденные номера; found_and_passed = номера, где ВСЕ результаты PASS
- not_found = etalon_numbers − found_in_launch (эталонные тесты, отсутствующие в запуске)
- all_failed_numbers = номера с хотя бы 1 не-PASS результатом; K = len(all_failed_numbers)

Определение: «уникальных номеров с падениями» = номер имеет хотя бы 1 результат со статусом не-PASS. Если у номера 3 Examples (2 FAIL + 1 PASS) — он входит в all_failed_numbers, в @-списке — 1 раз, в детальной таблице — 2 строки (только FAIL-результаты).

Per-team (если teams > 1): total/passed/failed/broken/skipped/unique_failed для каждой команды.

Присвоение команды: каждый результат привязан к ровно ОДНОЙ команде — по полю Team. Номер с результатами в разных командах: в статистике — по каждой команде; в @-списке — 1 раз, в команде с БОЛЬШИМ числом не-PASS; в детальной таблице — отдельные строки по командам.

Строка «Итого» — СУММА по рассматриваемым командам, НЕ total_results запуска:
- Итого.Рез = Σ команда.Рез; Итого.PASS/FAIL/BROKEN/SKIP — аналогично
- Итого.Уник. = len(объединение all_failed_numbers по всем командам)
- Итого.% PASS = Итого.PASS / Итого.Рез × 100 (аналогично FAIL/BROKEN)

→ CP2 (полнота): PASS + FAIL + BROKEN + SKIP = total (ТОЧНЫЕ цифры, без «~»).

## 5. Группировка по ошибкам (первое совпадение сверху вниз)

| 2 | Таймаут выполнения | execution expired; Failed to open TCP connection; Connection timed out; getaddrinfo; Net::ReadTimeout |

| 4 | Ошибка утверждения | expected:.*got:; AssertionError; expected not to find; ОР:.*ФР:; не выделена красным; не включает в себя |
| 5 | Ошибка тестовых данных | Не удалось создать клиента; отсутствует в таблице; undefined method; nil:NilClass; NoMethodError |
| 6 | Элемент не описан в коде | не описан в коде; не описан в page object |

| 12 | Несовпадение данных | не совпадает; не соответствует; отличается от ожидаемого |
| 13 | 500 Internal Server Error | 500 Internal Server Error; 500 ошибк |
| 14 | Без сообщения | Пустое/отсутствующее message |
| 15 | Пропущено (SKIP) | статус SKIP |

Правила:
- #3 выше #4 (баг ведущего нуля); #10–#12 выше #13/#14. Не попадает ни под один паттерн — создать новую именованную группу (1–5 слов из сути ошибки).
- Группируются FAIL + BROKEN по РЕАЛЬНЫМ message (п.3.4). ЗАПРЕЩЕНО группировать по придуманным причинам.
- SKIP классифицируется как группа №15 «Пропущено (SKIP)» — отдельной строкой в сгруппированной таблице §7.2A (без детализации причин); это сохраняет равенство «объединение тегов таблицы == @-список» (§7.2A/§7.2B).
- Один номер с разными ошибками в разных Examples — попадает в несколько групп.
- Единицы строк: в @-списке и BROKEN-таблицах — уникальные НОМЕРА; в FAIL-таблицах и на Странице 2 — каждый РЕЗУЛЬТАТ отдельной строкой.
- **Классы §5 И ЕСТЬ строки сгруппированной таблицы Страницы 1 (§7.2A)** — колонка «Ошибка» = имя класса, «Теги» = все номера группы, «Кол-во» = число результатов. Конкретные параметры (xpath/хост:порт/даты) НЕ дробят класс на отдельные строки — остаются частью тегов.

Валидация «Без сообщения» (обязательна при >10 результатах): перепроверить исходное поле message в TestOps; если есть — отнести к группе #1–#13 или создать новую; пусто — оставить. Осталось ≤5 → пройдена; >10 → предупредить пользователя. Целевой порог: ≤5% без классификации.

## 6. Формирование результата (в памяти/из nonpass_results.jsonl)

КРИТИЧНО — ПОЛНОТА ВЫВОДА: агент ОБЯЗАН вывести ВСЕ не-PASS номера в @-списке и детальной таблице. Вывод только FAIL без BROKEN — ОШИБКА. Вывод только наблюдений без номеров — ОШИБКА.

6.0. ПРЕДВАРИТЕЛЬНЫЙ РЕЗУЛЬТАТ В ЧАТ: после прохождения верификации по эталону (п.3.6) и до публикации вывести предварительный проверенный результат в чат (статистика + @-список + сводка по типам ошибок), НЕ прерывая размышления и НЕ дожидаясь подтверждения пользователя — продолжать к ФАЗЕ 2. Пользователь видит результат в чате параллельно с публикацией. В этот предварительный вывод ОБЯЗАТЕЛЬНО включить строку-вердикт верификации из п.3.6.

6.1. Статистика: Всего {total} | PASS {p} | FAIL {f} | BROKEN {b} | SKIP {s} | Уникальных с падениями {K}

Per-team таблица (если teams > 1):

| Команда | Рез. | PASS | FAIL | BROKEN | SKIP | Уник. | % PASS | % FAIL | % BROKEN |
|---------|:----:|:----:|:----:|:------:|:----:|:-----:|:------:|:------:|:--------:|
| T9 | {n} | {p} | {f} | {b} | {s} | {u} | {p/n×100}% | {f/n×100}% | {b/n×100}% |
| TX | {n} | {p} | {f} | {b} | {s} | {u} | {p/n×100}% | {f/n×100}% | {b/n×100}% |
| **Итого** | **{N}** | **{P}** | **{F}** | **{B}** | **{S}** | **{U}** | **{P/N×100}%** | **{F/N×100}%** | **{B/N×100}%** |

Формулы «Итого»: N = Σ n по командам (НЕ total_results запуска); P/F/B/S — аналогично; U = количество уникальных номеров с падениями (объединение множеств); % PASS = P / N × 100. % = значение / total команды × 100, округлить до 1 знака. Строка «Итого» — ОБЯЗАТЕЛЬНА.

6.2. Сводка по типам ошибок (Группа | Результатов | Номеров).

6.3. FAIL-таблицы с реальными сообщениями (по командам). Столбцы: № | Тест | Suite | Ошибка. Тест — номер (префикс Suite до пробела); Suite — часть после номера; Ошибка — ТОЛЬКО реальное message из п.3.4 (обрезать до 300 символов, xpath сокращать до последнего значимого сегмента).

6.4. BROKEN-таблицы по ТИПАМ ОШИБОК (единый формат для детальной таблицы Страницы 1 см. §7.2A). Столбцы: Ошибка (класс §5) | Кол-во результатов (ТОЧНОЕ число, без «~») | Тесты (номера с @).

6.5. @-список: ВСЕ не-PASS номера (FAIL + BROKEN + SKIP) через пробел с @, каждый РОВНО 1 раз. Группировка по командам (номер с результатами в двух командах — в команде с бОльшим числом не-PASS); сортировка — ЕСТЕСТВЕННАЯ по числовым компонентам слева направо (НЕ «по алфавиту»: 10.02.01 идёт после 02.xx). Верификация по эталону — п.3.6. len(@-список) == K.

6.6. Ключевые наблюдения (3–5):
1. % инфраструктурных падений: (Таймаут ожидания элемента + Таймаут выполнения) / not_passed × 100%. Если > 50% — явно указать
2. Блоки с одинаковым root cause (3+ теста с одной ошибкой)
3. Повторяющиеся баги (формат даты, статус и т.д.)
4. Домены с >30% падений
5. Стабильно падающие тесты (если есть данные)

6.7. Проверка полноты: «Из {N} {тип}-тестов {team_display_name} найдено {M}, не найдено в запуске {not_found_count}, упало {K} уникальных номеров ({not_passed} результатов)». Новые тесты: «Рекомендуется обновить файл эталона: @{номера}».

6.8. Контроль полноты вывода — ОБЯЗАТЕЛЕН перед ФАЗОЙ 2 (жёсткие гейты; расхождение = БЛОК):
1. len(@-список) == K
2. Сумма «Кол-во» в сгруппированной таблице == not_passed_results; объединение тегов == @-список == K (каждый не-PASS результат ровно в одной группе)
3. Каждая группа ошибок из Шага 5, с ≥1 результатом, представлена в таблице
4. Для каждого FAIL-результата причина — реальное сообщение
5. Все номера в @-списке ∈ etalon (или подтверждены пользователем) — инструментально по п.3.6
6. PASS + FAIL + BROKEN + SKIP == total
7. complete == true (манифест скана, гейт из п.3.2b)

→ CP2 (вывод): все пункты пройдены → ФАЗА 2.
