# Режим: разбор запуска

> Часть скилла `testops-analysis`. Общие правила — `../SKILL.md`.
> Детали сбора данных (§1–§6), краевые случаи и чек-лист ошибок — `run-analysis-details.md`. Форматы страниц — `confluence-templates.md`.

## 🔴 Пути: где лежат скрипты, эталоны и артефакты

`<QA_HOME>` — корень скилла (определяет `scripts/_paths.py`: env `QA_HOME` → родитель папки `scripts/`).
Артефакты прогонов — вне репозитория: `~/.qa-artifacts/` (env `QA_ARTIFACTS_ROOT`, флаг `--root`).

| Что | Где |
|---|---|
| скрипты, правила | `<QA_HOME>/scripts/`, `<QA_HOME>/config/` |
| эталоны команд | ветка `qa-analysis-data` (`AUTOTEST/sfa`, `etalons/<TEAM>/etalon_<тип>.txt`) → кэш `~/.qa-artifacts/etalons/<TEAM>/` |
| командные Jenkins-джобы | `<QA_HOME>/config/team_jobs.json` (версионируется) |
| персональные джобы (fallback) | `~/.qa-artifacts/autotesters.json` |
| артефакты прогонов | `~/.qa-artifacts/launches/…`, `~/.qa-artifacts/reruns/…` |

**Полная картина** — пути, поток данных, справочник скриптов, диагностика: `toolkit-guide.md`.
**Контракты артефактов** (кто пишет / кто читает): `../config/contracts/README.md`.

## Назначение

Из запуска TestOps достать тесты ПЕРЕДАННЫХ команд по эталонному списку, сформировать @-список в строчку, посчитать статистику с процентами и опубликовать в Confluence:
- **Страница 1** — сводка (§7.2): per-team статистика → @-список для Jenkins → сгруппированная таблица ошибок `| Ошибка | Кол-во | Теги(@) |`. Отдельная секция системных падений НЕ создаётся (§7.2C). Разбор прогона (по типам ошибок) — на фазе rerun (режим классификации перезапуска).

**Команды (teams) и путь к эталону передаются на вход** — скилл не зашит под конкретные команды. Пример для T9/TX приведён в Конфигурации как дефолт.

## Критические правила (эмпирически доказаны; нарушение = заведомо неверный результат)

> Инварианты — краткая сводка. Детальный источник и порядок действий — секции §1–§9; здесь правила НЕ дублируют их целиком.

1. **Эталон — файл в кэше оператора, папка на команду:** `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt`, где `<TEAM>` — ASCII-имя папки команды, `<тип>` — тип тестов (QG/HF/RM). Источник истины — ветка `qa-analysis-data` (`AUTOTEST/sfa`, `etalons/<TEAM>/etalon_<тип>.txt`), кэш скачивает `scripts/fetch_etalons.py`; в репозитории скилла эталонов нет. Структура: папка на команду, внутри файлы по типам (`BIT`/`TAMUL`/… ; `T9`+`TX` → папка `TX-T9`, файлы `etalon_HF.txt`/`etalon_QG.txt`/`etalon_RM.txt`). Читать через локальный `read`. **НЕ Confluence** (страницы содержат лишние номера чужих команд — реальный кейс: 58 ложных «упавших»). Эталон выбирается по команде (папка) и типу (имя файла); номер — по имени теста. Контроль эталона — формат (N>0, паттерн, уникальность) + пересечение с запуском; файлов-конфигов нет.
2. **Пагинация — size=100** (максимум API). size>100 молча обрезает вывод (реальный кейс: 18 из 157). Обязателен **гейт хвоста** (п.3.8) — хвост запуска классическая зона тихой потери данных.
3. **Двойной фильтр обязателен**: Team ∈ teams И номер ∈ etalon. Эталон — ЕДИНСТВЕННЫЙ источник истины о принадлежности теста к команде; поле Team — только дополнительный сторож.
4. **Реальные сообщения об ошибках** — только из данных API (шаги / поле message). Запрещено придумывать причину падения.
5. **Полный скан НЕ отдавать субагенту одному.** Скан, сверка множеств, счёт статистики и сборка отчёта выполняются скриптами этого скилла (они пишут артефакты на диск) — субагент обрезает большие результаты и теряет хвост. Делегировать можно только чтение уже сохранённых артефактов по offset/limit и узкие read-only проверки; передавать субагенту «сделай весь разбор» — запрещено.
6. **Запрет `confluence_update_page`** на страницу-родителя (confluence_page_id): она содержит эталонный список; перезапись = потеря данных. Публикация — только созданием НОВЫХ дочерних страниц.
7. **Гейты полноты — жёсткие**: len(@-список) == K; строк в детальной таблице == not_passed_results; complete == true (манифест скана). Любое расхождение — БЛОК публикации и возврат к шагу 3, а не «допустимое отклонение».
8. **Заголовки и строка «Запуск» формируются ИЗ `launch.name`** — ЕДИНСТВЕННОГО источника: заголовки страниц «Анализ прогона {launch.name}» / «Разбор прогона {launch.name}», строка «Запуск: {launch.name} {team_display_name}». Запрещён хардкод типа (QG/HF/RM) и ключевых слов («регрессионного») в контенте — они дублируют `launch.name` и могут разойтись с фактическим именем запуска.
9. **🔴 Клиринг типа и команд ДО скана — всегда при сомнениях**. Агент ОБЯЗАН явно уточнить у пользователя **тип тестов** (HF/QG/RM — если он неоднозначен: не прочитан из launch.name, размыт, противоречив между источниками) и **команду/список команд** (например, «T9», «TX», «T9,TX» — если не задано явно, названо обобщённо или непонятно, для скольких команд ведём разбор), КАЖДЫЙ раз, когда есть хоть какое-то сомнение. Это НЕ «угадать и продолжить»: эталон строится от команды (п.1), тип влияет на интерпретацию сообщений и статистику — неверный вход = заведомо неверный скан. **Запрещено приступать к чтению эталона, выбору скриптовых аргументов и сканированию TestOps, пока оба поля (тип и команды) не однозначны** — при неоднозначности ОСТАНОВКА и вопрос пользователю через `question` (батчем оба поля, не по отдельности). Основание догадываться «по аналогии» / «по прошлому разу» нет: каждый запуск уточняется независимо. Если инструмент `question` недоступен (например, вызов из субагента) — ОСТАНОВИТЬСЯ и задать вопрос текстом в ответе; угадывать запрещено.
10. **🔴 Перезапуск упавших — fan-out по КОМАНДНЫМ Jenkins-джобам (ФАЗА 3), персональная джоба — fallback.** Основной путь: `scripts/dispatch_team_reruns.py` по реестру `config/team_jobs.json` берёт `expected_set.json` каждой команды (`launches/{id}/{team}/`), собирает per-team @-список и запускает джобу `DEBUG/<TEAM>` (`tags` через ПРОБЕЛ, `env=qa`, **`parallel=15`, `rerun=1`**). Результат — `launches/{id}/dispatch.json`: статусы и ссылки на сборки. Подробно — `dispatch.md`. Fallback (команды нет в реестре / разбор по тегу тестировщика): персональная джоба из `~/.qa-artifacts/autotesters.json`; записи нет — СПРОСИТЬ ссылку и ЗАПОМНИТЬ (❌ не угадывать). Запуск — ТОЛЬКО при непустом @-списке (K>0) и после публикации (CP3). 🔴 `parallel=15` обязательно: дефолт джобы `parallel=1` небоевой (прогон часами).
11. **🆕 Фильтр по ТЕГУ ТЕСТИРОВЩИКА (опционально, OR с командой).** Скилл МОЖЕТ сузить/расширить выборку по тегу тестировщика: тест включается, если `(Team ∈ teams И номер ∈ etalon)` **ИЛИ** `тег тестировщика ∈ теги testcase`. Тег — **один**, задаётся флагом `--tester-tag "<tag>"` (напр. `abodrykh`). 🔴 **Тег спрашивать у пользователя** (как тип/команду), если разбор ведётся «по моим тестам», а тег не задан явно — НЕ угадывать (доменный логин вида `u_xxxx` ≠ тег в TestOps; теги тестировщиков обычно совпадают с `@автором` в feature-файлах). В tag-ветке **эталон НЕ требуется** (тег самодостаточен: тест включается по тегу, даже если номера нет в эталоне). Старый путь (без `--tester-tag`) не меняется.

## Инфраструктура артефактов и локальные скрипты (OpenCode)

Вся тяжёлая механика (пагинация, сверка множеств, гейт хвоста, публикация) выполняется через локальные Python-скрипты из `<QA_HOME>/scripts/`. Скрипты — НЕ субагенты: запрет делегирования (п.5) на них не распространяется, они ОБЯЗАТЕЛЬНЫ.

> **🔴 Правило №0 — НЕ пиши код с нуля. Сначала ищи готовое.**
> 1. **До написания ЛЮБОГО скрипта** — `glob *.py` в `<QA_HOME>/` и осмотри перечень готовых.
> 2. **Используй готовый скрипт как есть**, если он покрывает шаг. Ниже (§ Шаги разбора) каждый шаг жёстко привязан к готовому имени скрипта.
> 3. **НЕ пиши код с нуля**, если целевое поведение достижимо готовым скриптом или его адаптацией. Есть готовое → используй его, а не генерируй аналог.
> 4. Свой скрипт — ТОЛЬКО при явном обосновании «готового нет, шаг не покрыт»; писать в `<QA_HOME>/temp/`, не в корень. «Я не посмотрел перечень» — НЕ обоснование.
> 5. Черновики/временные генераторы — только в `temp/`, по готовности отчёта удалять (см. «Политика хранения»).

> **Плейсхолдеры путей:** `<QA_HOME>` — корень скилла `testops-analysis` (в репозитории `skills/testing-skills/testops-analysis`, после установки `~/.config/opencode/skills/testops-analysis`: там scripts/, config/). Точное значение даёт `scripts/_paths.py`. Артефакты прогонов и эталоны — ВНЕ скилла: `~/.qa-artifacts/` (env `QA_ARTIFACTS_ROOT` или флаг `--root`), эталоны — в `~/.qa-artifacts/etalons/`. 🔴 НЕ зашивать абсолютный путь в скилл: скрипты определяют <QA_HOME> сами (env QA_HOME → родитель папки scripts/, см. scripts/_paths.py). Эталоны — `<artifacts root>/etalons/<TEAM>/etalon_<тип>.txt`, скачиваются `fetch_etalons.py` из ветки `qa-analysis-data`. Два имени команды: team_display_name (T9+TX, для отображения) ≠ имя папки эталона (TX-T9, для пути) — не путать.

- **Корень артефактов:** `~/.qa-artifacts/` (вне репозитория, у каждого оператора свой). Структура: `launches/{launch_id}/` (общий: исторические `at_list.txt`/`case_meta.json` первичного анализа команд), `launches/{launch_id}/{team}/` (**🔴 пер-командные снимки: `expected_set.json` + `nonpass_results.jsonl` + `scan_manifest.json`**), `reruns/{rerun_id}/` (диффы), `etalons/<TEAM>/etalon_<тип>.txt` (**кэш эталонов из ветки**, скачивает `fetch_etalons.py`), `config.json` (опционально: base URL/токен TestOps, имена веток/каталогов данных), `stability.jsonl` (история метрики стабильности).
- **Состояние передаётся только через `~/.qa-artifacts/`.** Confluence — витрина для людей; НЕ парсь HTML для передачи состояния между режимами — читай `expected_set.json`.
- **Скрипты (папка `<QA_HOME>/scripts/`, все `.py` в одной папке — они импортируют друг друга; использовать как есть, п. Правило №0):**
  - `scan_testops.py` — пагинация (size=100) + двойной фильтр (Team ∈ teams после нормализации И номер ∈ etalon) → `launches/{launch_id}/{team}/nonpass_results.jsonl` (ТОЛЬКО не-PASS) + `launches/{launch_id}/{team}/scan_manifest.json` + `launches/{launch_id}/{team}/expected_set.json` (полная картина по номерам команд со статусами и `pass_rate`) + `stability.jsonl`; в stdout — только статистика и пути. 🔴 **пишет ТОЛЬКО в папку команды `{team}/`, НЕ в общий `launches/{launch_id}/`** (иначе сканы разных команд перезаписывают `expected_set.json` друг друга). Запуск: `python scan_testops.py --launch-id {id} --teams "T9,TX" --etalon "{путь к etalon_<тип>.txt}" [--tail-check]` (эталон — файл из кэша `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt`).
    - **🆕 `--tester-tag "<tag>"` (OR-фильтр по тегу тестировщика):** тест включается, если `(Team ∈ teams И номер ∈ etalon)` **ИЛИ** `testCaseId ∈ тест-кейсы с этим тегом`. Теги берутся один раз через AQL `GET /api/testcase/__search?rql=tag="<tag>"` (пагинация, множество `testCaseId`). В `expected_set.json` у каждого номера появляется `origin` (`team`/`tag`/`both`), в корне — `tester_tag`. В manifest: `tagged_testcases`, `included_by_tag`. Без флага — прежнее поведение (команда+эталон) бит-в-бит. В tag-ветке эталон опционален.
  - `verify_sets.py` — сверка @-списка с эталоном: `python verify_sets.py --at-list "{...}/at_list.txt" --etalon "~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt"` → вердикт `ЧИСТО` / `ЕСТЬ ЛИШНИЕ` (exit 0/1) + тот же числовой блок, что в п.3.6.
    - **🆕 tag-режим:** `python verify_sets.py --at-list "{...}/at_list.txt" --expected-set "{...}/{team}/expected_set.json"` → референс = `expected_numbers` из артефакта (надмножество команды и тега). Обязателен, когда скан шёл с `--tester-tag` (иначе номера tag-ветки вне эталона дадут ложное «ЕСТЬ ЛИШНИЕ»).
  - **`render_markdown.py`** — детерминированный markdown Страницы 1 (§7.2: статистика → @-список §7.2B → детальная таблица не-PASS) из `expected_set.json`. Публикации в Confluence НЕ делает: готовый текст агент вставляет через MCP `atlassian` (шаблоны и гейты — `references/confluence-templates.md`). Запуск: `python render_markdown.py --expected-set ".../launches/{launch_id}/{team}/expected_set.json" --out <file>`. Статистику, @-список и классы ошибок считает сам скрипт (из `counts`/`statuses`; классы — через `classifier.py`). Если в папке `expected_set.json` лежит `skip_diagnosis.json` — подхватывает его и печатает блок «⚠️ Прогон НЕПОЛНЫЙ» **первым**, до статистики, с разбивкой причин пропуска (`--no-diagnosis` отключает). Режим `--dispatch <dispatch.json>` рендерит страницу «AI run {launch.name}» из артефакта раздачи.
  - **`diagnose_skips.py`** — ПОЧЕМУ тесты эталона не участвовали в прогоне: `python diagnose_skips.py --launch-id {id} [--team {TEAM}]` → `launches/{id}/{team}/skip_diagnosis.json` + таблица «Причина | Тестов | Что делать». Слои: (A) своя сборка — `jobRun` запуска → Jenkins API (`result`, `Aborted by` в консоли, переданные `tags`); (B) свой репозиторий — `git ls-tree` ветки `master` (`AUTOTEST/sfa`), поиск `<номер>.feature` и признак `features/excluded` (такой тест перезапуск не подхватит никогда). Закрытый список исходов; неустановленная причина печатается как «не установлено», не додумывается. С другими запусками НЕ сверяется (правило 15a-тер).
  - `diff_rerun.py` — режим классификации перезапуска (дифф рерана), здесь не используется.
  - `export_team_etalons.py` — выгрузка эталона команды из прогона (использовать при отсутствии эталона в кэше, Fallback п.2.3; бутстрап §3.9). Пишет в кэш `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt`; источник истины — ветка, перенос — PR.
  - `update_etalon.py` — дополнение эталона подтверждёнными новыми тестами (§3.9): `--etalon <путь> --add "номер ..."` или `--input <json [{number,name}]>`; дедуп + естественная сортировка + `.bak`-копия, идемпотентно.
  - `fetch_etalons.py` — выгрузка эталонов из ветки `qa-analysis-data` (`AUTOTEST/sfa`, `etalons/`) в кэш: `fetch_etalons.py [--team TX-T9] [--type QG] [--refresh] [--check] [--list]`. Нужен git-доступ к `AUTOTEST/sfa` (креды git оператора); `--check` работает без сети.
  - `doctor.py` — предполётная проверка окружения (см. ниже «Контракт ресурсов»); запускать первым делом на новой машине.
  - `classify_rerun.py` — используется режимом классификации перезапуска; здесь не вызывается.
  - **`dispatch_team_reruns.py`** — раздача перезапусков по КОМАНДНЫМ джобам: читает `expected_set.json` каждой команды, запускает `DEBUG/<TEAM>` (`tags` через ПРОБЕЛ, `env=qa`, `parallel=15`, `rerun=1`), пишет `launches/{id}/dispatch.json`. Подробно — `dispatch.md`.
  - `team_canon.py` — единый нормализатор имён команд (транслит кириллицы `ТММБ`→`TMMB`, срез префикса `SFA Команда`, алиасы `T9/TX`→`TX-T9`). Модуль: импортируется `scan_testops`/`export_team_etalons`/`dispatch_team_reruns`, сам по себе не запускается.

## § Шаги разбора (жёсткая последовательность: шаг → готовый скрипт → действие)

> Жёсткая привязка «шаг N → подключить готовый скрипт → сделать X». Шаг считается выполненным только после инструментального гейта. См. Правило №0.

**Шаг 1 — Осмотр репы и окружения (обязательный старт).**
`glob *.py` в `<QA_HOME>/`. Убедись, что на месте `scan_testops.py`, `verify_sets.py`, `render_markdown.py` (и в наличии эталон команды в кэше `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt`; нет — `python fetch_etalons.py --team <TEAM> --type <тип>`). Если скрипта не хватает — сообщить пользователю, НЕ заменять самоделкой и НЕ переписывать скрипт с нуля.

Затем `python doctor.py`: строка `СТАТУС: ОШИБКА` — это повод **остановиться и предложить установку/настройку** (правило 14, `toolkit-guide.md` § Окружение), а не идти дальше с дырами.

**Шаг 2 — Клиринг типа и команд.** Тип (HF/QG/RM) — из `launch.name`; команды — из запроса. 🆕 **Если разбор ведётся «по моим тестам» — уточнить ТЕГ тестировщика** (флаг `--tester-tag`, напр. `abodrykh`); не угадывать по логину. При сомнении — `question` (батчем: тип, команды, тег). Не переходить к скану, пока входы не однозначны (правило 9/11, CP1).

**Шаг 3 — Эталон.** Путь в кэше: `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt` (скачать/обновить: `python fetch_etalons.py --team <TEAM> --type <тип> [--refresh]`). Загрузить (read), контроль: N>0, номера по паттерну, уникальны (см. `run-analysis-details.md` §2.2). После скана — проверка пересечения с запуском. Иначе «Не тот файл» → уточнить.

**Шаг 4 — Скан — `scan_testops.py`.**
`python scan_testops.py --launch-id {id} --teams "{Команда}" --etalon "{эталон}" --tail-check` (🆕 добавить `--tester-tag "{tag}"` для OR-фильтра по тестировщику).
Скрипт сам пишет `expected_set.json` + `nonpass_results.jsonl` + манифест. Проверить манифест: `complete == true`, `tail_mismatch == false`. Иначе — пересканировать (1 повтор), потом стоп.

> **Если прогон ещё идёт** — не ждать в чате: `watch_launch.py --launch-id {id} --teams "{...}" --type {тип}`
> дождётся готовности (счётчики стабильны, `total > 0`) и сам выполнит шаги 4 и 8 (и реран при `--wait-rerun`).

**Шаг 5 — Картина по номерам/командам.** Использовать `expected_set.json` (уже посчитан: `counts`, `statuses`, `pass_rate`). НЕ пересчитывать «в голове». @-список = не-PASS номера из `expected_set.json` (формат при публикации — с `@`, префикс ставит `render_markdown.py`).

**Шаг 5a — 🔴 Контроль ПОЛНОТЫ ОХВАТА (обязателен, до любых выводов).** Из `scan_manifest.json` взять
`etalon_covered`, `etalon_total`, `etalon_coverage_etalon_pct`, `etalon_missing_count`,
`etalon_missing_numbers`. Если `etalon_missing_count > 0`:
- **первой фразой ответа** сказать: «прогон неполный — N из M тестов команды в нём не участвовали»
  (и то же первым блоком в отчёте: `## ⚠️ Прогон НЕПОЛНЫЙ`);
- **не писать** «остальные проходят» / «дефектов не найдено» — у этих тестов нет статуса;
- выполнить **Шаг 5b (диагноз пропуска)**;
- спросить/сообщить: нужен ли добор этих тестов в перезапуск (`--include-missing`).

Эта проверка ловит главную ошибку разбора — принять «тест не запускался» за «тест в порядке».
Подача важна не меньше расчёта: реальный кейс, где 130 из 282 тестов отсутствовали, был замечен
пользователем только потому, что он сам сверил списки, — блок шёл сноской под статистикой.

**Шаг 5b — 🔴 Диагноз пропусков (обязателен при `etalon_missing_count > 0`).**
`python diagnose_skips.py --launch-id {id} [--team {TEAM}]` → `launches/{id}/{team}/skip_diagnosis.json`
+ таблица «Причина | Тестов | Что делать». Отвечает на вопрос «перезапускать или чинить»:
тест, отключённый в репозитории (`features/excluded`), не запустится **никогда** — его нельзя
отправлять в перезапуск. Сборка, вычищенная ротацией логов, даёт «не установлено» — это нормально,
причина не выдумывается. Сверка с другими запусками — **только с разрешения пользователя** (правило 15a-тер).

### Политика хранения артефактов (перезапись, а не плодить)

Контрактные источники по `launch_id  + команда` **перезаписываются** в той же фиксированной папке `launches/{launch_id}/{team}/`, история снимков не копится. 🔴 **Каждая команда — своя подпапка `{team}/`**; общий `launches/{launch_id}/` хранит только исторические `at_list.txt`/`case_meta.json` первичного анализа ВСЕХ команд, но НЕ снимки `expected_set`/`scan_manifest`/`nonpass` (они всегда в `{team}/`). Причина: сканы разных команд одного запуска затирали `expected_set.json` друг друга (реальный кейс — TREX затёр TX).

| Артефакт | Политика |
|---|---|
| `{team}/expected_set.json`, `{team}/nonpass_results.jsonl` | **перезаписывать** (актуальный снимок команды одного запуска) |
| `{team}/at_list.txt` | перезаписывать |
| `{team}/case_meta.json` | перезаписывать |
| `{team}/scan_manifest.json` | **НЕ перезаписывать** — единственный честный гейт полноты, «сертификат» конкретного скана; приложение к свежему скану пишется как новый (версия/время) |
| `page*.md/html`, `table*.txt`, `_*.py`, черновики | **не создавать в корне/`launches/`** — временный транзит писать в `temp/`, по готовности отчёта удалять/перезаписывать |

Правила:
1. НЕ плодить разовые генераторы `_*.py` в корне скилла. Временные скрипты и промежуточные отчёты — в `<QA_HOME>/temp/` (или системный temp), по готовности удалять.
2. `scan_manifest.json` — только один актуальный на команду/запуск; при повторном скане НЕ подменять старый, если он был `complete` (иначе теряется гейт). Повторный скан того же id/команды пишет `scan_manifest_{ts}.json`.
3. Итоговые отчёты для публикации держать в памяти → публиковать → `temp/` очищать, выживают только `*.json`/`*.jsonl`/`case_meta.json` в `launches/{id}/{team}/`.
4. **При командах >1 в запуске**: перед сканом/чтением проверять содержимое целевого `expected_set.json` (`teams`, длина). Не использовать/не перезаписывать чужую команду.

## Архитектура: две фазы + временное хранилище

- ФАЗА 1 — ЧТЕНИЕ (только read-операции): вход → эталон → история (`fetch_results`) → TestOps → контроль полноты → группировка → результат в памяти/на диске.
- ФАЗА 2 — ПУБЛИКАЦИЯ (только create-операции): запись в базу результатов (`publish_results --push`), при необходимости — страницы Confluence.

Переход ФАЗА 1 → ФАЗА 2 — ТОЛЬКО после прохождения CP2. Если CP2 не пройден — вернуться к шагу 3 (ФАЗА 1).

### Принцип «сырьё не тащится в дорогой контекст»

Ключевой механизм защиты от когнитивной перегрузки и потери данных. Тяжёлые сырые данные (постраничный скан TestOps) НЕ удерживаются и НЕ передаются целиком через границу контекста. Они оседают в **артефакте скана на диске** (`nonpass_results.jsonl` + `scan_manifest.json`, п.3.2) или в «холодной памяти» извлекающего шага, а до итогового анализа доходит только компактная не-PASS-выборка. Это снижает перегрузку главного агента и даёт **проверяемый след** для детерминированной сверки полноты.

Два взаимодополняющих инструмента этого принципа:
- **Артефакт скана** (штатный, не аварийный) — детерминированный материал для сверки полноты: `complete == true` (манифест, п.3.2b).
- **Инструментальная верификация @-списка** (п.3.6) — механическая сверка каждого номера с эталоном, обязательная строка-вердикт.

Что из этого — «в голове», а что — «в окружении»: все подсчёты полноты (len, R == N, set-diff ∈ etalon) выполнять ИНСТРУМЕНТАЛЬНО (read/grep по файлу/эталону), а не «помню, что это было».

**7.7. Контракт состояния `case_meta.json` (ОБЯЗАТЕЛЬНО после публикации):**
Один файл на пару `launch_id + team`: `~/.qa-artifacts/launches/{launch_id}/{team}/case_meta.json`.
Все режимы читают и дописывают **этот** файл — второго `case_meta.json` не существует.
🔴 Путь — ПОДПАПКА команды `{team}/`, не общий `launches/{launch_id}/`.
Схема полей — `config/contracts/case_meta.schema.json` (единственный источник истины).

```json
{
  "run": {
    "launch_id": 1095599,
    "launch_name": "<имя запуска>",
    "team": "<Команда>",
    "page1_id": "<id страницы «Анализ прогона…»>",
    "parent_page_id": 3703816519,
    "artifacts_path": "<абсолютный путь папки команды; берётся из expected_set.json>",
    "published_at": "2026-11-12T23:10:00"
  },
  "dispatch": {
    "jenkins_jobs": [{"team": "<Команда>", "job": "DEBUG/<TEAM>", "build_url": "<url>", "tests": 96}],
    "dispatched_at": "2026-11-12T23:15:00"
  },
  "rerun": null
}
```

| Секция | Кто пишет | Когда |
|---|---|---|
| `run` | режим разбора запуска | после CP3 (Шаг 10) |
| `dispatch` | режим раздачи перезапусков | после раздачи (Шаг 11) |
| `rerun` | режим классификации перезапуска | при разборе рерана (дописывает, не перезаписывает чужое) |

Правила:
- `run.page1_id` — главный контракт: реран **обновляет** именно эту таблицу, не создаёт новую.
- `run.artifacts_path` — копируется из `expected_set.json` (его пишет `scan_testops.py`); не вычислять путь повторно.
- `rerun` на первичном запуске — `null`; заполняется при разборе: `{"rerun_launch_id": ..., "page2_id": ..., "verdict_at": ...}`.
- Дописывание секции = прочитать файл, заменить **свою** секцию, сохранить остальные без изменений.
  Потеря чужих секций — ошибка (данные предыдущих фаз).
- Записывается после CP3, проверяется в CP4. Если запись невозможна — НЕ критично для первичной публикации,
  но сообщить пользователю, что реран без `case_meta` потребует ручной передачи `page1_id`.

**7.8. ФАЗА 3 — РАЗДАЧА перезапусков по КОМАНДНЫМ Jenkins-джобам (после CP3):**
Основной путь — fan-out по джобам команд, а не запуск «одной персональной джобы на всё».
Детали формата, статусов и кодов возврата — `dispatch.md`.

**Почему командные джобы.** Упавшие принадлежат разным командам, у каждой своя джоба
`DEBUG/<TEAM>` со своим составом и своими владельцами сборки. Запуск в чужой/персональной
джобе смешивает ответственность и ломает маршрутизацию результатов.

**Шаги ФАЗЫ 3:**
1. **План (без сети и кредов):** `py -X utf8 <QA_HOME>/scripts/dispatch_team_reruns.py --launch-id {id} --dry-run`.
   Печатает по командам: `task`/`folder`, `count`, `status=would_trigger`. Ничего не пишет.
2. **Проверить план:** команды со статусом `unmapped`/`duplicate_scan` — это решение человека
   (дописать джобу в `config/team_jobs.json` либо включить `merge_folders`).
3. **Боевая раздача:** та же команда без `--dry-run`. Пишет `launches/{id}/dispatch.json`
   (per-team @-списки, статусы, `build_url`). `skipped_empty` — норма: у команды нет упавших.
4. **Страница «AI run {launch.name}»:** `render_markdown.py --dispatch <dispatch.json> --launch-url <url>`
   → вставка через MCP `atlassian` (дочерняя к Странице 1). Числа вручную не переписывать.
5. **Ссылки на сборки** — в чат и в `case_meta.json` (§7.7): `jenkins_job` + `rerun_build_url`.

**Гейты запуска (все обязательны):**
- публикация Страницы 1 прошла (CP3);
- @-список команды непуст (`K > 0`) — пустые команды не дёргаются (`skipped_empty`);
- `env = qa`, `parallel = 15`, `rerun = 1` — передавать явно, НЕ полагаться на дефолты джобы
  (`parallel=1` — прогон часами, `rerun=0` — флейки в отчёте);
- `tags` — строка с `@` через **ПРОБЕЛ** (не запятая).

**Exit 1 ≠ провал раздачи.** `dispatch.json` записан, остальные команды ушли в Jenkins;
проблемные перечислены в отчёте.

**Свойства целевой джобы (контракт, подтверждён на `DEBUG/Bodrykh_with_testops`):** параметры
`tags` (String — список через пробел, с `@`), `env` (Choice — стенд), `browser`/`browserVersion`
(Choice), `parallel` (String), `rerun` (String), `branch` (String). 🔴 `env` — Choice БЕЗ дефолта →
передавать явно (`qa`).

**Fallback — персональная джоба:** используется, только если команды нет в `team_jobs.json`
(`unmapped`) или разбор идёт по тегу тестировщика. Реестр — `~/.qa-artifacts/autotesters.json`
(вне репозитория, у каждого оператора свой; образец — `config/autotesters.example.json`):
`{ "Bodrykh": { "job": "DEBUG/Bodrykh_with_testops", "env": "qa", "parallel": "15", "rerun": "1" } }`.
Принимается и короткий формат (`"Bodrykh": "DEBUG/..."`). Записи нет → СПРОСИТЬ ссылку и
ЗАПОМНИТЬ (файл + Memory, тег `project:testops-analysis`). URL → fullname: отбросить
`.../view/<View>/`, склеить сегменты после каждого `job/`.

**Идемпотентность:** повторная раздача того же `launch_id` при неизменном @-списке даёт
`already_dispatched` и переиспользует ссылку; принудительно — `--force`.

**Запреты ФАЗЫ 3:**
- ❌ Запускать при `K == 0` (дефолтный `tags` джобы запустит полный прогон).
- ❌ Полагаться на дефолты джобы (`parallel=1`, `rerun=0`) — передавать `15`/`1` явно.
- ❌ Угадывать джобу «по аналогии» — при отсутствии записи только спросить и запомнить.
- ❌ Подставлять дефолтный `tags` джобы — всегда явный @-список команды.
- ❌ Менять `env` на что-то кроме `qa` без явного указания пользователя.
- ❌ Парсить HTML Jenkins-UI — только MCP (`get_item`/`build_item`/`get_build`).
