# Режим: классификация перезапуска

> Часть скилла `testops-analysis`. Общие правила — `../SKILL.md`.

## 🔴 Пути: где лежат скрипты, эталоны и артефакты

`<QA_HOME>` — корень скилла (определяет `scripts/_paths.py`: env `QA_HOME` → родитель папки `scripts/`).
Артефакты прогонов — вне репозитория: `~/.qa-artifacts/` (env `QA_ARTIFACTS_ROOT`, флаг `--root`).

| Что | Где |
|---|---|

| эталоны (кэш) | `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt` — скачивает `fetch_etalons.py` из ветки `qa-analysis-data` |

## Назначение

Режим разбора запуска (`run-analysis.md`) сформировал таблицу упавших тестов и опубликовал Страницу 1 в Confluence. Упавшие перегнали в Jenkins, перезапуск завершился и выдал новый (узкий) rerun-запуск в TestOps. **Главная цель ЭТОГО скилла — отделить одно от другого** для каждого снова-упавшего теста и разложить по трём типам, чтобы быстро группировать тесты по важности:

| Тип | Суть | Кто чинит | Приоритет |
|---|---|---|---|
| **Ошибка системы / инфраструктуры** | Окружение: таймауты TCP, execution expired, 500 от среды, элемент не появился из-за нагрузки/сети | Инфраструктура / DevOps | Низкий для кода тестов |
| **Ошибка автотеста** | Баг в самом тесте: NoMethodError, неверный/устаревший локатор, ошибка в page object | Автор теста (QA-автоматизатор) | Средний — чинится в коде теста |
| **Дефект / баг продукта** | Падение из-за неверной логики SFA: несоответствие ожидаемого/фактического, формат даты, некорректный статус | Разработка продукта | Высокий — заводить дефект |

Группировка по этим трём типам напрямую даёт «важные / не очень»: дефекты → тикеты разработке; ошибки автотеста → чинить сами тесты; системные → смотреть окружение, часто «не наш тест».

Выполняется **отдельным проходом** от режима разбора запуска (свежий контекст), работает с **той же группой тестов** через родительскую страницу Confluence. Статус снова-упавших **НЕ меняется** — меняется/обогащается классификация и причина.

## Критические правила

0. **🔴 УТОЧНЯТЬ ССЫЛКИ И ВХОДЫ ПРИ ЛЮБОМ СОМНЕНИИ — ДО скана и публикации.** Родительская страница разная для КАЖДОГО прогона (свой «Анализ прогона …» на каждый rerun) — `page1_id` НЕ угадывать и не подставлять «по аналогии с прошлым разом». Обязательно уточнять у пользователя (батчем, `question`) всякий раз, когда хоть что-то неоднозначно:
   - **ссылка/ID родительской страницы** («под какой страницей анализа публиковать разбор?») — если `case_meta.json` не найден, содержит чужой/старый `page1_id`, либо есть >1 кандидата;
   - **ID rerun-запуска и первичного запуска** (какой именно реран разбираем; с чем сравнивать);
   - **команды и тип (HF/QG/RM)** — если не читаются однозначно;
   - **путь к `expected_set.json`** — если в запуске несколько команд/несколько кандидатов;
   - **репозиторий/ветка для git-верификации** (`git_repo`) — если не задан по умолчанию.
   При неоднозначности — **ОСТАНОВКА и вопрос**, НЕ продолжать с предположением. «Похоже/наверное/в прошлый раз было так» — НЕ основание. Подтверждённые входы фиксировать в `case_meta.json` (contract).
1. **Источник истины — артефакт `expected_set.json`** (`~/.qa-artifacts/launches/{launch_id}/{team}/expected_set.json`), созданный режимом разбора запуска (содержит `expected_numbers`, `statuses`, `messages`). Родительская страница Confluence (таблица §7.2A + @-список §7.2B) — витрина; её парсинг — ТОЛЬКО fallback, если JSON отсутствует. НЕ пересчитывать «кто упал» самостоятельно.
2. **Полный скан rerun-запуска обязателен** (пагинация до total_results + гейт хвоста) — иначе нельзя отличить PASS от «теста нет в запуске».
3. **Тест, отсутствующий в rerun = не участвовал = ИГНОРИРОВАТЬ** (не трогать статус, не заполнять, НЕ считать вылечившимся).
4. **Снова-упавший тест → статус НЕ меняется.** FAIL остаётся FAIL, BROKEN остаётся BROKEN (меняется/обогащается КЛАССИФИКАЦИЯ и причина). **BROKEN классифицируется и поясняется так же, как FAIL** — на каждый BROKEN дать причину и один из трёх типов; ЗАПРЕЩЕНО сжимать все BROKEN одной строкой «упали с теми же ошибками» без разбора. **Вылечившийся (PASS в rerun), наоборот, изменяет статус в ОСНОВНОЙ таблице на `PASS`** — он пройден, а не остаётся упавшим.
5. **Классификация — детерминированная, а не догадка.** Каждый тест получает ровно один тип из {система, автотест, дефект} на основе (a) текста ошибки и (b) верификации в git. Вывод должен быть **подкреплён** сообщением из API и/или локусом в коде (файл:строка), иначе помечается «не подтверждено».
6. **Запрет `confluence_update_page` на родителя с эталоном** (3703816519). Только дочерняя Страница 1 (`parent_page_id`).
7. **Реальные причины** — только из rerun-запуска и кода репозитория; без выдумки.
8. **🔴 ЧАТ-FIRST: основной результат — вердикт в чате; публикация опциональна и ТОЛЬКО по явному подтверждению.** Скилл по умолчанию ЗАВЕРШАЕТСЯ выдачей полного вердикта в чат (Шаг 7). Публикация в Confluence (обновление основной + создание/обновление дочерней страницы) выполняется ТОЛЬКО если пользователь явно попросил («публикуй», «оформи страницу»). Авто-публикация запрещена. План/вердикт выводится в чат заранее (без публикации), чтобы пользователь видел результат до любого действия в Confluence.
9. **Не создавать новых колонок.** Таблица остаётся `Название | Статус | Причина падения`; тип выносится в группировку/сводку, а не в отдельную колонку.
10. **Публикация разбора — ДОЧЕРНЯЯ под страницей анализа, БЕЗ дублей.** Страница «Разбор рерана …» создаётся/обновляется **дочерней под соответствующей страницей анализа** (её `page1_id` — вход, подтверждённый пользователем, см. правило 0). Повторный прогон **обновляет** ту же страницу (поиск по title среди детей родителя), а НЕ создаёт вторую. 🔴 **Родитель КАЖДЫЙ раз разный** — брать `page1_id` из `case_meta.json` ТОЛЬКО если `rerun_id` этого разбора совпадает; иначе **спросить пользователя**. Штатный путь: `classify_rerun.py --scan ... --chat` (вердикт) → `render_markdown.py --rerun-diff ... --classification ...` (готовый markdown) → публикация через MCP `atlassian` (`create_page`/`update_page_section`), см. `confluence-templates.md`. Родителя с эталоном (3703816519) и саму страницу анализа НЕ перезаписывать.

## Вход

- `new_launch_id` — ID rerun-запуска в TestOps (результат перепрогона Jenkins).
- `parent_page_id` — ID дочерней Страницы 1 Confluence «Анализ прогона…» от режима разбора запуска.
  **Приоритет источника (детерминированный):**
  1. `launches/{launch_id}/{team}/case_meta.json` → `run.page1_id` — авторитетный ID таблицы для обновления (путь берётся из `expected_set.json` → `artifacts_path`, не вычисляется повторно);
  2. входной `parent_page_id` — только если `case_meta.json` отсутствует;
  3. **вопрос пользователю** — если ни одного источника нет, либо `run.team` в файле не совпадает с анализируемой командой.
- `expected_set_path` — путь к `~/.qa-artifacts/launches/{launch_id}/{team}/expected_set.json` (launch_id первичного запуска, team — команда rerun-анализа; если неизвестен — найти свежайший `launches/*/{team}/expected_set.json` или спросить). **ВНИМАНИЕ:** корректный путь — внутри ПОДПАПКИ команды; если в `launches/{launch_id}/` есть `expected_set.json` без команды и он не совпадает по `teams` с анализируемой командой — он НЕ источник (затёрт другой командой), восстановить из Confluence.
- Тип HF/QG, teams — определяются ИЗ `expected_set.json` (поле `teams`) и rerun-запуска (по правилам режима разбора запуска). **НЕ зашиты жёстко:** скилл работает с тестами любой команды/команд, которые присутствуют в `expected_set`. Команда учитывается только в классификации (по полю Team результата) и в статистике, если их несколько.

## Выход

- **Обновлённая ОСНОВНАЯ страница Confluence** (`parent_page_id`): в её таблице вылечившиеся при реране меняют статус на `PASS` + «перезапуск успешен»; снова-упавшие статус НЕ меняют; не участвовавшие не тронуты; @-список обновлён.
- **Дочерняя страница (побочная)** — результат ГЛУБОКОГО АНАЛИЗА: сводка-классификация сверху (Дефекты / Автотест / Системные) + детальные блоки по каждому снова-упавшему (номер, команда, статус, ошибка, анализ: вердикт типа + ссылки на похожие падения), сгруппированные по трём секциям.
- В чат — план изменений (до публикации) и итоговая классификация с дельтой.

## Шаги

### Шаг 1 — Чтение expected_set (источник истины)
Прочитать `expected_set_path` (JSON): `expected_numbers` (номера с `@`), `statuses` (текущий статус каждого), `messages` (причина из первичного прогона), `teams`. Это и есть `expected_set` — те, кого гнали в Jenkins, с их текущими {статус, причина}. НЕ парсить HTML-таблицу Confluence, пока JSON существует.
**🔴 Проверить команду:** поле `teams` JSON должно содержать анализируемую команду, а `len(expected_numbers)` — соответствовать. При расхождении (затёрт другой командой) → пересканировать (режим разбора запуска) в папку нужной команды `launches/{id}/{team}/expected_set.json`; если это невозможно — fallback на Confluence (см. ниже). Никогда не использовать `expected_set.json` чужой команды из общего `launches/{id}/`.

**Fallback (ТОЛЬКО если JSON отсутствует):** `confluence_get_page(parent_page_id)`. Извлечь из таблицы (§7.2A) + @-списка (§7.2B) набор текущих не-PASS тестов → `expected_set`, с их текущими {статус, причина}.

**Эталон ожидаемого формата таблицы (§7.2A, колонки `№ | Название | Статус | Причина падения`):**
```
| № | Название | Статус | Причина падения |
|---|----------|--------|-----------------|
| 1 | @04.02.01.01 | FAIL | expected: "Продажа в SFA" got: "Ожидает обработки" |
| 2 | @10.79.13.01.01 | BROKEN | Unable to find visible xpath |
...
```
Правила извлечения: номер — после `@` в колонке «Название»; статус — из колонки «Статус» (`FAIL`/`BROKEN`/`SKIP`); причина — из колонки «Причина падения`. Строки таблицы — каждый не-PASS результат.

### Шаг 2 — Гейт полноты набора
При JSON-источнике (Шаг 1, основной путь) гейт тривиален: `expected_numbers` уже согласован со `statuses`/`messages` — сверка не нужна. Диагностика ниже — для fallback-парсинга Confluence.
Детерминированный парсинг; `len(expected_set)` согласуется с @-списком. Не сходится → БЛОК + **диагностика** (не просто «не сходится»):
- какая структура ожидалась (эталон в Шаге 1: колонки `№ | Название | Статус | Причина падения`, номера с `@`);
- что найдено по факту: число колонок/строк, наличие `@`-префиксов, сходимость извлечённых номеров с @-списком;
- вероятная причина (сменился формат разбора запуска / разметка сломана) и сообщение пользователю.

Если таблица найдена, но формат отклоняется от эталона — сообщить о расхождении, НО продолжать, если номера извлекаются корректно (устойчивая эвристика); жёсткий БЛОК — только если номера/статусы не извлекаются.

### Шаг 3 — Скан rerun + дифф через `diff_rerun.py`
Запустить:
```
python diff_rerun.py --launch-id {new_launch_id} --expected-launch-id {launch_id}
```
Скрипт сам: проверяет имя/готовность запуска, делает полный постраничный скан rerun (size=100, гейт полноты `complete`), сопоставляет с `expected_set.json` и сохраняет `~/.qa-artifacts/reruns/{new_launch_id}/rerun_diff.json` с секциями `healed` / `failed_again` / `skipped` / `absent` и `stats`. В stdout — только статистика. ЗАПРЕЩЕНО итерировать `testops_launch_list_test_results` в контекст постранично.

### Шаг 4 — Гейт полноты перезапуска
Из `rerun_diff.json` (stats): `present` (healed + failed_again + skipped) и `absent` — не участвовали (игнорировать, не заполнять). Вывести «Не участвовали (игнорируются): {номера}» (секция `absent`).
`stats.consistent == true` (present + absent == expected_count) — обязательный гейт; `false` → БЛОК: проверить маппинг номеров, пересканировать.

### Шаг 5 — Разделение по результату rerun (из `rerun_diff.json`)
Анализировать ТОЛЬКО компактный JSON (не сырой скан):
- **`healed`** (все Examples PASS в rerun) → **вылечился**: ячейка Статуса = `PASS`, ячейка Причины = «перезапуск успешен». (Классификация не нужна.)
- **`failed_again`** (есть FAIL/BROKEN, либо SKIP-как-не-PASS) → **снова упал**: статус НЕ менять; направить в Шаг 6 (классификация). `status` и `messages` — из JSON.
- **`skipped`** → разделить на два вида:
  - **Намеренный SKIP** (маркер `@skip`/`pending`, явная причина «skipped intentionally», не выполнено продукт-условие) → **НЕ классифицировать**, НЕ включать в снова-упавшие; вывести отдельно «Пропущено намеренно: {номера}».
  - **SKIP из-за ошибки** (упало предусловие / ошибка окружения до теста) → трактовать как не-PASS → в Шаг 6 (классификация).
  Детект намеренности: сначала по `hint_intentional` и тексту причин из JSON (дёшево); если неясно — через git (поиск маркера skip в файле теста).

### Шаг 6 — Классификация снова-упавших

Слой 1 (тип по правилам) считает скрипт `classify_rerun.py`; слой 2 — узкая
git-проверка очереди `needs_evidence`. Полная схема, форматы `evidence` и
`verdicts`, шкала confidence (V2), кластеры и рендер — `rerun-classifier-details.md`.

```
py -X utf8 classify_rerun.py --rerun-id {rerun_id} --scan --chat
```

### Шаг 7 — ВЫВОД ВЕРДИКТА В ЧАТ (ОСНОВНОЙ РЕЗУЛЬТАТ; публикация — опциональна)

> 🔴 **ЧАТ-FIRST (закреплено).** Основной и достаточный результат работы скилла — **вердикт в чате**. Публикация в Confluence НЕ является обязательной и по умолчанию **НЕ выполняется**: скилл завершает работу, выдав полный вердикт в чат, и переходит к публикации ТОЛЬКО по **явному подтверждению пользователя** (см. Шаг 8). Никаких авто-публикаций «на всякий случай».

Вывести в чат ПОЛНЫЙ вердикт в едином формате (группами, не по тестам):
1. **Шапка:** `Разбор рерана — {launch.name} ({team_display_name})`; одной строкой: `Снова упали: Z | Вылечились: Y | Не участвовали: U`.
2. **Сводка-таблица** по типам (с долями) + строка покрытия evidence:
   `| Тип | Кол-во | Доля |` → Дефекты / Ошибки автотеста / Системные / Триаж (low);
   `Покрытие evidence: подтверждено (high/medium) H% · триаж (low) L%`.
3. **Разбор по ГРУППАМ** (п.6.1а: 1 блок на класс ошибки, представитель + список остальных номеров), сгруппировано по трём секциям-подзаголовкам — «🔴 Дефекты продукта», «🟡 Ошибки автотеста», «⚪ Системные», внутри каждой по возрастанию. Формат блока — тот же, что ниже (Ошибка / Упавший шаг / Анализ / **Confidence** / Обоснование / Рекомендация / **Routing**).
4. **❓ Триаж (low confidence)** — отдельным списком: что не удалось подтвердить + краткая причина. Не выдаётся за тип.
5. **Вылечившиеся:** {номера} → PASS, «перезапуск успешен».
6. **Не участвовавшие / пропущено намеренно** — игнорируются (если есть).
7. **Новый @-список** (оставшиеся не-PASS после перезапуска), по возрастанию — готов для следующего Jenkins-прогона (ФАЗА 3 режима разбора запуска).
8. **Финальная строка:** `Публикация в Confluence: НЕ выполнена. Скажи «публикуй» — оформлю дочернюю страницу разбора и обновлю основную таблицу.` (см. Шаг 8).

Метрика качества классификации (от Z): `Подтверждено (высокая/средняя) X% | Триаж (low) Y% | Инструмент недоступен W%`. Подтверждено = тип однозначен + подкреплён evidence-строкой (API и/или git); Триаж = «файл не найден»/низкий score; Инструмент недоступен — отдельный статус (не входит ни туда, ни туда).

BROKEN-номера включаются в списки наравне с FAIL — каждый с типом и причиной, а не строкой «упали с теми же ошибками».

### Шаг 8 — ПУБЛИКАЦИЯ (ОПЦИОНАЛЬНО; ТОЛЬКО по явному подтверждению пользователя)

> 🔴 **Выполняется ТОЛЬКО если пользователь явно попросил публикацию** после Шага 7 («публикуй», «оформи страницу»). Без такой просьбы — скилл ЗАВЕРШАЕТСЯ на Шаге 7 (вердикт в чате). Публикация = отдельное осознанное действие.

Две операции (обе после подтверждения), **В СТРОГОМ ПОРЯДКЕ: сначала ОСНОВНАЯ, потом ДОЧЕРНЯЯ.**

**Порядок и обработка сбоев (компенсация рассинхрона):**
1. Сначала ОСНОВНАЯ (авторитет статусов). 
2. Только после успешной ОСНОВНОЙ — ДОЧЕРНЯЯ.
3. ОСНОВНАЯ прошла, ДОЧЕРНЯЯ упала → основная корректна, не откатывать; дочернюю перегенерировать и дописать отдельным проходом, сообщить.
4. Упала ОСНОВНАЯ (критично) → ДОЧЕРНЮЮ **НЕ публиковать вовсе** (сохранить консистентность «основная не тронута → дочерняя не создаётся»), сообщить пользователю.
5. Шаг 9 — обязательная верификация ОБЕИХ страниц; при рассинхроне разобрать и починить, НЕ оставлять как есть.

**(А) ОБНОВИТЬ ОСНОВНУЮ страницу** — `confluence_update_page(parent_page_id, ...)`:
- **вылечившиеся → статус в ОСНОВНОЙ таблице меняется на `PASS`** + причина «перезапуск успешен» (тест пройден — обновляется, а НЕ остаётся упавшим);
- снова-упавшие → статус в основной таблице НЕ меняется (остаются FAIL/BROKEN);
- не участвовавшие — не тронуты;
- обновить @-список (убрать вылечившихся); родителя с эталоном НЕ трогать.

**(Б) Создать или обновить ДОЧЕРНЮЮ страницу** — результат глубокого анализа ТОЛЬКО снова-упавших:
- сводка-классификация сверху (Дефекты / Автотест / Системные);
- **разбор по ГРУППАМ ошибок** (п.6.1а): на КАЖДУЮ группу — 1 глубокий блок (представитель + список остальных номеров), а не блок на каждый тест. Глубокий формат блока ниже, сгруппирован по трём секциям-подзаголовкам («Дефекты», «Ошибки автотеста», «Системные»), внутри каждой — по возрастанию.

Итог: ОСНОВНАЯ таблица — актуальные статусы (пройденные → PASS), ДОЧЕРНЯЯ — разбор причин снова-упавших (глубокий анализ).

**Формат блока по ГРУППЕ (1 глубокий блок на группу ошибок):**
```
@{представитель} — {название теста} (+ {N} тестов в группе: @01 … @02)
Команда: {Team}
Статус: {FAIL/BROKEN}
Ошибка: {реальное message из rerun}
Упавший шаг: {шаг, где упало} + {статус/время}
Анализ: {вердикт типа: система/автотест/дефект + что чинить + ссылка на похожие падения}
Confidence: {high|medium|low} (score {Σ весов}: {перечень evidence})
Обоснование: {декод ошибки (что тест ждал) + кросс-шаги (что прошло/упало) + стабильность (та же ошибка в первичном прогоне?) + git-локус + git-история (менялся ли локус, кем/когда) + исключение системы}
Рекомендация: {что проверить и как принять решение — завести дефект / обновить тест / отдать окружению}
Routing: {owner_team} · {severity} · {action} · {where} · критерий: {criterion}
```

Пример:
```
@10.31.06 — Автоматическое создание коммуникаций …
Команда: TX
Статус: BROKEN
Ошибка: Unable to find visible xpath ".//tr[./td[@headers='a2']...]"
Упавший шаг: «Проверили, что таблица "Текущие задачи" содержит…» — FAIL (12.4s); далее SKIP
Анализ: Дефект продукта (или устаревший тест) — коммуникация ЕСТЬ, но содержимое не совпало
Обоснование: шаг ожидания коммуникации прошёл (0.7s), а проверка строки упала → элемент присутствует, данные иные; та же ошибка в первичном прогоне → стабильно; без таймаутов/сети → не окружение
Рекомендация: сверить фактические значения в таблице с ожиданиями теста; если логика изменилась — дефект, иначе — обновить тест
```

Поле **Анализ** = ВЕРДИКТ ТИПА (система / ошибка автотеста / дефект + что чинить и куда смотреть) + ССЫЛКИ НА ПОХОЖИЕ ПАДЕНИЯ (номера тестов с той же/похожей причиной, чтобы сразу видеть кластер). Для каждого снова-упавшего — отдельный блок; блоки в секции соответствующего типа.

**Сводка-классификация** (сверху ДОЧЕРНЕЙ страницы): `Снова упали: Z → Дефекты: D | Ошибки автотеста: AT | Системные: S | не подтверждено (триаж): NC`.
Плюс строка **покрытия evidence:** `Подтверждено (high/medium): H% | Триаж (low): L% | Инструмент недоступен: U%`.

### Шаг 9 — Верификация (CP после записи; ТОЛЬКО если публикация выполнялась)

🔴 Выполняется ТОЛЬКО после Шага 8. Если публикации не было (чат-first, по умолчанию) — Шаг 9 пропускается, скилл завершён на Шаге 7.

Перечитать ОСНОВНУЮ (`confluence_get_page(parent_page_id)`) и ДОЧЕРНЮЮ страницы. Проверить:
- **ОСНОВНАЯ:** вылечившиеся получили статус `PASS` + «перезапуск успешен»; снова-упавшие сохранили FAIL/BROKEN; не участвовавшие не тронуты; @-список обновлён (без вылечившихся).
- **ДОЧЕРНЯЯ:** сводка на месте; по каждому снова-упавшему — блок в формате выше; секции (Дефекты/Автотест/Системные) на месте; блоки в порядке возрастания; на группах high/medium присутствуют **Confidence**, **Routing** и evidence-строки; low — в секции триажа.
- Расхождение → переформировать (с подтверждением); родитель с эталоном не тронут.

### Шаг 10 — Запись в базу результатов (обязательно, даже без Confluence)

Классификация рерана — единственный источник причин падений, поэтому результат
пишется в базу `qa-analysis-data` (даже если страницы Confluence не создавались):

```powershell
# план + локальная запись
py -X utf8 <QA_HOME>\scripts\publish_results.py --team <TEAM> --type <HF|QG|RM> --launch-id <первичный> --rerun-id <реран>

# публикация в ветку — после подтверждения пользователя
py -X utf8 <QA_HOME>\scripts\publish_results.py --team <TEAM> --type <HF|QG|RM> --launch-id <первичный> --rerun-id <реран> --push
```

- Причины попадают как `suspected` (или `confirmed`, если есть evidence: git-локус, дефект, ручная проверка).
- Повторная публикация того же прогона идемпотентна (`no-changes`), счётчики не раздуваются.
- База накопительная: следующая классификация читает `causes.jsonl` команды и видит частоту/типовые фиксы.

## Контрольные точки

- **BP1** (перед сканом): `expected_set.json` прочитан, `expected_set` согласован (или fallback-парсинг Confluence прошёл с диагностикой).
- **BP2** (после скана): полный скан, `present`/`absent` разделены, сумма корректна.
- **BP3** (после классификации): каждый снова-упавший отнесён ровно к одному типу, вывод подкреплён (API и/или git) или помечен «не подтверждено». 🔴 Confidence посчитан по шкале evidence (6.0в-скоринг); низкий (low) → триаж; на каждую high/medium-группу есть evidence-строки и routing.
- **BP4** (перед публикацией): вердикт выведен в чат (Шаг 7); публикация выполняется ТОЛЬКО по явному подтверждению пользователя (по умолчанию скилл завершается на Шаге 7).
- **BP5** (после записи): только если публикация была — перечитано, статусы корректны, секции/сводка на месте, эталон не тронут.

## Статистика с дельтой

«Было упавших: {N} → перепрогнано: {M} → вылечились: {Y} → снова упали: {Z} → из них: Дефекты {D}, Ошибки автотеста {AT}, Системные {S}, не подтверждено {NC} → не участвовали: {U}».

## Схема доступа к git (репозиторий sfa)

- Проект: `AUTOTEST`, репозиторий: `sfa` (`https://example.invalid`).
- Обзор: ТОЛЬКО точечно по известному пути (`bitbucket_list_directory_content(workspace=AUTOTEST, repository=sfa, path=<конкретная директория>)`); НЕ для слепого блуждания по дереву.
- Локальный клон sfa (если доступен): `rg -n "<query>" <путь к клону>` — быстрый поиск и чтение контекста найденных файлов.
- Чтение файла: `bitbucket_get_file_content(workspace=AUTOTEST, repository=sfa, file_path=<путь>, start_line=..., line_count=...)`.
- Поиск по номеру/названию теста: `bitbucket_grep(workspace=AUTOTEST, repository=sfa, query=<номер/ключевое>, branch=<default>)` или `bitbucket_search_code`.
- **История локуса (V1, 6.1б):** `bitbucket_get_file_blame(workspace=AUTOTEST, repository=sfa, file_path=<путь>, start_line=..., line_count=...)` — автор/дата по строкам; локальный клон — `git blame -L`/`git log -L`. Даёт evidence `git_history`.
- Связать номер теста из TestOps с файлом: искать по номеру в имени файла/в теле, по названию теста, по сути шагов. Соглашение «номер ↔ файл» может быть неполным — поиск эвристический, результат помечать как найденный/не найден.

## Краевые случаи

| Ситуация | Действие |
|---|---|
| Тест не участвовал в rerun | Игнорировать, не заполнять, «не участвовали» |
| Все вылечились | Все PASS + «перезапуск успешен», сводка без «снова упали» |
| Тест снова упал, git не находит файл | Пометить «не подтверждено (файл не найден)», рекомендация человеку |
| Текст ошибки выступает в 2 категории | Спор — решать через git; если не решается — «не подтверждено» |
| 0 результатов в rerun | Все из expected = не участвовали; ничего не менять; сообщить, что перезапуск не отработал |
| Пользователь отклонил подтверждение | Не публиковать, остановиться |
| Запуск не завершён | Подать как предварительный снимок, подтверждение перед записью |
| Examples с разными статусами | Тест вылечился, только если ВСЕ Examples PASS; иначе в снова-упавшие, классифицировать |
| Падение из-за данных в git | Если видно, что тест ожидает неверных данных → ошибка автотеста, файл:строка |

## Чек-лист ошибок

| Ошибка | Симптом | Защита |
|---|---|---|
| Отнесение xpath-таймаута к системе без проверки локатора | ложный «система» при битом локаторе | git-верификация спорных (правило 5, 6.3) |
| Игнор не-перегнанного теста как «вылечился» | ложный PASS | правило 3: не участвовал ≠ PASS |
| Смена статуса снова-упавшего | теряется факт повторного падения | правило 4: статус не меняется |
| Сжатие всех BROKEN одной строкой «упали с теми же ошибками» без разбора | BROKEN-тесты остаются без пояснений и типа | правило 4, шаг 6: каждый BROKEN классифицируется и получает причину + тип |
| «Самостоятельное решение» без подкрепления | галлюцинация типа | подкрепление API и/или git + пометка «не подтверждено» |
| Спорный тип решён только эвристикой, без git | твёрдый вердикт без кода | глубина (6.1б) НЕ заменяет git (6.3) для expected/xpath строки; спор — только через git |
| Глубокий разбор на каждый тест вместо группы | раздувание контекста и токенов | 6.1б: глубина только на ПРЕДСТАВИТЕЛЯ группы, остальные ссылаются на вердикт |
| Вердикт без evidence | галлюцинация confidence | 6.0в-скоринг: confidence = Σ весов evidence; low → триаж, не выдаётся за факт |
| «Почему упало именно сейчас» без git-истории | пропуск регрессии | 6.1б GIT-ИСТОРИЯ (blame): менялся ли локус, кем/когда |
| Запуск V3 на всех группах | лишний расход бюджета | 6.1в: V3 (timeline) ТОЛЬКО для owner=дефект и при наличии истории/реп |
| Рекомендация без адресата | «чините» без кому/критерия | routing-объект (owner_team/severity/action/where/criterion) обязателен |
| Использование `expected_set.json` из общего `launches/{id}/` затертого чужой командой | классификация по чужим тестам / неверная статистика | правило командной изоляции: читать `launches/{id}/{team}/expected_set.json`, проверять `teams`; при расхождении — fallback на Confluence |
| Перезапись родителя с эталоном | потеря эталона | правило 6 |
| Публикация без подтверждения | необратимая ошибка | правило 8, BP4 |
| Создание новых колонок | раздувание | правило 9: только секции/сводка |

## Границы

- НЕ пересчитывает полный вывод с нуля (это режим разбора запуска).
- НЕ трогает эталон и родителя с эталоном.
- НЕ делает статус снова-упавших (не меняет).
- НЕ создаёт новых колонок.
- НЕ обрабатывает тесты, не участвовавшие в rerun (игнорирует).
- НЕ делает глубокий разбор на каждый тест — глубина (декод/кросс-шаги/стабильность) применяется к ПРЕДСТАВИТЕЛЮ группы, остальные ссылаются на вердикт.
- НЕ галлюцинирует классификацию — типы подкреплены API и/или git, иначе «не подтверждено».
- НЕ выдаёт low-confidence вердикт за подтверждённый — он уходит в триаж человеку.
- НЕ публикует ничего в Confluence без явной просьбы пользователя (чат-first; по умолчанию работа завершается вердиктом в чате).
- НЕ запускает V3 (regression timeline) вне групп `owner=дефект`.
