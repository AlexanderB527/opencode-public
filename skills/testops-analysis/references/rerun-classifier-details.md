# Классификация снова-упавших: детали (Шаг 6)

> Часть скилла `testops-analysis`, режим классификации перезапуска.
> Общие правила — `../SKILL.md`.
> Правила классов ошибок — `../config/classify_rules.json` (данные, не код).

### Шаг 6 — Классификация снова-упавших (гибридная схема: скрипт + узкий LLM)

> 🔴 **Слой 1 (тип по правилам) считает СКРИПТ `classify_rerun.py`, а не нейросеть.** Ручная классификация LLM давала невоспроизводимые результаты (один прогон — «система», другой — «автотест»). Правила детерминированы; LLM добивает ТОЛЬКО спорные через git (Слой 2), остаток → триаж человеку.

Классификации подлежит КАЖДЫЙ снова-упавший — и FAIL, и BROKEN (BROKEN не «отдельная категория»: для него так же берётся реальный message и один из трёх типов).

**6.0. Детерминированный Слой 1 — `classify_rerun.py`:**
```
py -X utf8 classify_rerun.py --rerun-id {rerun_id}
```
Скрипт из `rerun_diff.json` по каждому снова-упавшему считает: `error_class` (§5, первое совпадение), предварительный `owner` (**система/автотест/дефект/спор**), `confidence` (high/medium/low), `action`, извлекает `locator` (xpath/хост:порт). Пишет `reruns/{rerun_id}/rerun_classification.json` (ЕДИНЫЙ источник истины) + печатает матрицу и метрику `confirmed_pct/disputed_pct`. Правила владельца: TCP/`execution expired`/500/`Connection reset` → система; `не описан в коде`/`Ambiguous match`/nil/NoMethodError → автотест; формат даты → дефект; `Unable to find visible xpath`/expected-got/наличия в списке/состояния элемента/`Другое` → **спор** (решает git, не догадка).

**6.0а. Слой 2 — git-проверка ТОЛЬКО очереди `needs_evidence`:**
LLM НЕ разбирает всё заново. По каждому номеру из `needs_evidence`: взять `locator` из артефакта → `bitbucket_grep`/`search_code` по `AUTOTEST/sfa` → записать `evidence.json` (`{"@номер": {"verdict": "found"|"unfound"|"tool_unavailable", "ref": "файл:строка", "note": "..."}}`) → применить:
```
py -X utf8 classify_rerun.py --rerun-id {rerun_id} --evidence {evidence.json}
```
Правило воспроизводимо: **found** (локатор есть/актуален) → система; **unfound** (битый/устарел) → автотест; **tool_unavailable** → остаётся в триаже.

**6.0б. Остаток — триаж человеку:** всё, что осталось `category=unknown`, — список в артефакте с импактом (обычно единицы). Markdown для страницы 2 рендерит общий `render_markdown.py` (`--rerun-diff` + `--classification`); тот же текст печатает `classify_rerun.py --chat`.

**6.0б-такс. РАСШИРЕННАЯ таксономия (не 3 группы).** Классы §5 сворачиваются в **7 категорий**:
`infra` (стенд/сеть недоступны), `env` (сервис отдал ошибку/таймаут), `locator` (автотест: не найден элемент),
`testcode` (автотест: ошибка кода/данных теста), `product` (дефект продукта), `testdata` (тестовые данные),
`unknown` (не классифицировано → триаж). Плюс **двухуровневая группировка**: крупный root cause
(хост:порт, xpath, HTTP-статус, встречается ≥2 раз в классе) выделяется в отдельную строку
(напр. `Таймаут выполнения [sfa-at-linux-1:4444]` = 63), мелочь сливается в `[прочие]`.
Так «81 таймаут» превращается в «63 — стенд X, 12 — сервис Y, 6 — прочее».

**6.0г-гейт. ГЕЙТ СХОДИМОСТИ (перед публикацией, обязателен):** в `counts.gate_ok`
проверяется, что Σ count по группам == числу упавших И каждый номер ровно в одной группе
(нет дублей/потерь). `gate_ok=false` → БЛОК, не публиковать, разобраться.

**ВАЛИДНОСТЬ вердикта LLM:** каждый вердикт обязан нести `evidence` (цитата из API-`message` или
`файл:строка`). Без цитаты `confirmed=false` — вердикт помечается «не подтверждено», не выдаётся за факт.

**6.0в. LLM-вердикт, routing и рекомендации по группам (то, что делает разбор полезным):**
На каждую **группу** (класс §5) LLM формирует вердикт, адресную рекомендацию и записывает `verdicts.json`:
```json
{"<error_class|cluster_key|cluster_label|@номер>": {
   "owner": "система|автотест|дефект",
   "confidence": "high|medium|low",
   "verdict": "вердикт (может быть многострочным, НЕ обрезается)",
   "reason": "обоснование (декод ошибки / кросс-шаги / стабильность / git-локус / git-история)",
   "recommendation": "что и как чинить (может быть многострочной)",
   "steps": "опц.: что проверить по шагам (многострочно)",
   "files": ["опц.: файл:строка"],
   "ref": "файл:строка (для git-подтверждённых)",
   "routing": {"owner_team": "автотесты|продукт|инфра", "severity": "blocker|major|minor",
               "action": "завести дефект|обновить локатор|отдать инфре|перепроверить данные",
               "where": "файл:строка|сервис|хост:порт", "criterion": "как поймём, что починено"},
   "evidence": [{"kind": "message|steps|stability|git_locus|git_history|regression_commit", "ref": "…", "note": "…"}]}}
```
**🔴 Ключ вердикта — ЛЮБОЙ из:** `cluster key` / `cluster label` / `error_class` (общий на группу) **ИЛИ `@номер` / `номер`** (ТОЧНЫЙ пер-тестовый вердикт — для конкретного теста). Приоритет матча: (1) точный номер → item; (2) cluster key/label → кластеры; (3) error_class/group_label → группы. Пер-тестовая запись переопределяет только свой тест; остальные наследуют кластерный вердикт.
Применить: `py -X utf8 classify_rerun.py --rerun-id {rerun_id} --verdicts {verdicts.json} --chat`. LLM НЕ классифицирует заново — он обогащает уже посчитанные кластеры И пер-тестовые записи.

**6.0в-скоринг. 🔴 EVIDENCE-GATED CONFIDENCE (V2 — достоверность вместо догадки).**
`confidence` группы НЕ выбирается «на глаз» — он СЧИТАЕТСЯ из собранных evidence по фиксированной шкале:

| Evidence | Источник | Вес | Как собрать |
|---|---|:--:|---|
| `message` (реальный) | TestOps | 1 (**обязателен**) | поле message результата / последний упавший шаг |
| `steps` (кросс-шаги) | TestOps | +1 | шаги результата/сценария: что прошло до падения |
| `stability` (та же ошибка в ≥2 прогонах) | `stability.jsonl` / история запусков | +1 | сравнение с первичным/прошлыми прогонами |
| `git_locus` (`файл:строка`) | `AUTOTEST/sfa` (bitbucket) | +2 | локатор/ожидание найдены в коде |
| `git_history` (локус менялся, кем/когда) | `AUTOTEST/sfa` (blame/log) | +2 | `git blame`/log по найденному файлу |
| `regression_commit` (подозрительный коммит в окне) | git (V3, только дефект) | +2 | см. 6.1в |

Правило расчёта: `score = Σ весов` присутствующих evidence (message **обязателен** — без него группа идёт в «Без сообщения», score не считается):
- **high** — `score ≥ 4` (обычно git_locus + message + ещё один);
- **medium** — `score 2–3`;
- **low** — `score < 2` (только message, либо message+steps без git).
🔴 **low → группа идёт в ТРИАЖ ЧЕЛОВЕКУ и НЕ выдаётся за подтверждённый вердикт** (в сводке — отдельным списком). Каждая строка `evidence[]` обязательна для high/medium; вердикт без evidence-строки не принимается.
Это НЕ заменяет детерминированный Слой 1 (`classify_rerun.py`) — confidence обогащает уже посчитанные группы и служит гейтом «подтверждено vs триаж».

**6.0г. Режим вторичного запуска БЕЗ эталона (`--scan`):**
Если разбор нужен по САМОМУ запуску (не сравнение с первичным), а ожидаемого набора/эталона нет:
```
py -X utf8 classify_rerun.py --rerun-id {rerun_id} --scan [--teams "{T9,TX}"]
```
Скрипт сам сканирует весь запуск (все non-PASS, `message` из TestOps), строит те же группы §5 и `rerun_classification.json` (`mode: scan`). Далее — Слой 2 (`--evidence`) для спорных и LLM-вердикты (`--verdicts`), затем markdown через `render_markdown.py` и публикация через MCP `atlassian` (`confluence-templates.md`).

Далее (6.1–6.4) — углубление по группам и git-верификация; они уточняют Слой 2, но НЕ заменяют детерминированный Слой 1.

**6.1. Извлечь реальный message** из rerun (последний упавший шаг / поле message, приоритет как п.3.4 режима разбора запуска). Только факт. **Для BROKEN message извлекается точно так же** (таймаут, xpath, execution expired и т.п.) — он и есть основа классификации.

**6.1а. Группировка по паттерну ошибки — СЕМАНТИЧЕСКИЕ КЛАСТЕРЫ (экономия API и контекста):**
> 🔴 **Группировать по СМЫСЛУ ошибки, а не по номеру локатора.** Все `Unable to find visible xpath` на разных экранах = ОДИН кластер («элемент не найден»), а не N групп по конкретному xpath. Скрипт делает это детерминированно (`semantic_clusters` из `classify_rules.json` → `result["clusters"]`); LLM только именует кластер и пишет вердикт.

- **Кластер (детерминированно, скрипт):** `{key, label, owner, category, count, stable, flaky, new, numbers}`. Приоритет матча — по порядку в `semantic_clusters` (первое совпадение подстроки message). Нет совпадения → кластер = `error_class` (fallback).
- **На КАЖДЫЙ кластер — ОДНА git-верификация (6.3)**; вердикт распространяется на все тесты кластера.
- **Стабильность (авто, флаг `--expected-launch-id`):** `stable` = повтор с первичного прогона, `flaky` = в первичном PASS, `new` = не участвовал. Стабильность — сильнейший разделитель «дефект/система» (стабильно) vs «флейк» (разово).
- Если внутри кластера у теста message отличается от паттерна (несколько Examples, разный текст) — такой тест верифицируется отдельно.
- В анализе/выводе разбирается кластер целиком (label + список номеров + стабильность), глубина — на представителя (6.1б).

**6.1б. Глубокий разбор ПРЕДСТАВИТЕЛЯ группы (на каждую уникальную группу — 1 глубокий разбор; остальные тесты ссылаются на вердикт):**
Пайплайн глубины выполняется строго по шагам; каждый шаг даёт evidence-строку (см. 6.0в-скоринг):
- **Декод ошибки** — если message содержит xpath/локатор/данные, разобрать, ЧТО именно тест ожидал (например, колонки таблицы и ожидаемые значения). Даёт предметное «что тест ждёт». → evidence `message`.
- **Кросс-шаги** — сопоставить предыдущие/следующие шаги теста (их статус и время): например, шаг «подождали появления элемента» прошёл, а проверка содержимого упала → элемент ЕСТЬ, но содержимое не совпало. Это разводит «не появилось» (система) и «появилось с другими данными» (дефект/устаревший тест). → evidence `steps`.
- **Стабильность** — сравнить с первичным прогоном: та же ошибка в обоих запусках → стабильное воспроизведение (в пользу дефекта/устаревшего теста), только в одном → флак/окружение. → evidence `stability`.
- **Исключение системы** — нет таймаутов/500/сети, шаг быстрый → окружение исключить обоснованно.
- **git обязателен для спорных** (как expected X got Y / xpath): глубина анализ НЕ заменяет git-верификацию (6.3) — спорные типы подтверждаются локусом в коде (ожидания/локаторы актуальны?). Глубина даёт контекст, git — твёрдый вердикт. → evidence `git_locus` (`файл:строка`).
- **🆕 GIT-ИСТОРИЯ (blame/log) — «почему тест упал именно сейчас»:** по найденному в 6.3 файлу получить историю локуса: `bitbucket_get_file_blame(AUTOTEST/sfa, file_path, start_line, line_count)` (или локальный `git log -L`/`git blame` при наличии клона). Цель — увидеть, **менялся ли локатор/ожидание недавно** и кто менял:
  - локус **менялся** вскоре после последнего PASS теста → сильный сигнал «регрессия из-за правки теста/кода» (уточняет owner);
  - локус **стабилен давно**, а тест упал → вероятнее дефект продукта или флак окружения.
  → evidence `git_history` (`файл:строка`, автор/дата коммита). Без доступного blame → шаг пропускается (не выдумывать);
- **Рекомендация (ROUTING) — адресно, не общими словами:** по каждой группе заполнить routing-объект (см. 6.0в): `owner_team` (кому — автотесты/продукт/инфра), `severity`, `action` (завести дефект / обновить локатор / отдать инфре / перепроверить данные), `where` (файл:строка / сервис / хост:порт), `criterion` (критерий готовности — как поймём, что починено).

**6.1в. 🆕 V3 — REGRESSION TIMELINE (только для групп с `owner=дефект`, опционально/дорого):**
Для группы, классифицированной как **дефект продукта**, и ТОЛЬКО для неё, включить временную корреляцию — она отвечает на главный вопрос «после какого изменения сломалось»:
1. **Последний PASS теста** — взять из истории прогонов (`stability.jsonl` / прошлые `expected_set.json`) или спросить; зафиксировать дату/запуск.
2. **Окно регрессии** — интервал (последний PASS … первый FAIL).
3. **Коммиты в окне** — по релевантной репе (автотесты `AUTOTEST/sfa` — через bitbucket; продукт `SFAONPEGA/sfa-*` — если доступ есть) собрать коммиты в окне, затрагивающие подозрительный файл/сервис/экран (по `where` из routing).
4. **Корреляция** — если найден коммит, совпадающий по времени и области → evidence `regression_commit` (`коммит/автор/дата`), вердикт усиливается до high, в рекомендацию добавляется ссылка на изменение.
5. **Нет доступа/нет истории** → шаг пропускается честно, помечается «timeline недоступен» (НЕ выдумывать коммит). V3 **никогда не блокирует** разбор — это обогащение.
🔴 V3 включается ТОЛЬКО для `owner=дефект` и только когда доступны история/репы. Для системных/автотест-групп V3 не запускается (не тратить бюджет).

**6.2. Предварительная классификация по тексту ошибки** — карта паттернов (детерминированно):

| Паттерн текста ошибки | Предварительный тип |
|---|---|
| `execution expired`; `Failed to open TCP connection`; `Connection timed out`; `Net::ReadTimeout`; `getaddrinfo` | **Система** (сеть/окружение) |
| `500 Internal Server Error`; `Connection refused` (от окружения) | **Система** (окружение), если нет признака дефекта |
| `NoMethodError`; `undefined method`; `nil:NilClass` | **Ошибка автотеста** (код теста) |
| `Unable to find visible xpath`; `Unable to find visible field`; `not found in page object`; `не описан в коде` | **Спорно**: система (не прогрузилось) ИЛИ ошибка теста (битый локатор) → решает git |
| `expected: ... got: ...`; `AssertionError`; формат даты (без ведущего нуля); несовпадение статуса/ФИО/телефона | **Спорно**: дефект ИЛИ ошибка теста → решает git (ожидание верно? данные/предусловия корректны?) |
| `Ambiguous match`; `found \d+ elements` | **Ошибка автотеста** (неоднозначный локатор) |
| `element click intercepted` | **Ошибка автотеста** (или система) → уточнить в git |
| пусто / без message | «Без сообщения» — проверить в git, иначе «не подтверждено» |

**6.3. Верификация через git (`git_repo`, дефолт AUTOTEST/sfa)** — решает спорные категории и подтверждает остальные:

**Лестница попыток (ровно 3, перед пометкой «не подтверждено»):**
1. `bitbucket_grep(workspace=<git_repo.workspace>, repository=<git_repo.repository>, query=<номер теста>)` — поиск по номеру.
2. `bitbucket_search_code(... query=<название/ключевые слова>)` — поиск по названию теста / ключевым словам / телу.
3. Локальный `rg -n "<номер/префикс/фрагмент>" <клон sfa>` (если путь к клону известен) ИЛИ точечный `bitbucket_list_directory_content(path=<подозреваемая директория>)` → `bitbucket_get_file_content(...)`. ЗАПРЕЩЕНО обзор всего дерева для поиска файла.
- Любой инструмент упал (разрыв/таймаут) → повторить **1 раз**; при повторном сбое → статус **«инструмент недоступен»** (это НЕ «не подтверждено» — код мог быть, но инструмент не отработал).
- Только после всех 3 попыток без результата → «не подтверждено (файл не найден)».

- доступ: `bitbucket_list_directory_content` / `bitbucket_get_file_content` / `bitbucket_grep` / `bitbucket_search_code` по `git_repo`.
- **Найти инфраструктуру теста** (page object, файл, локаторы, предусловия) по номеру автора/названию.
- **Решить спор**: 
  - `Unable to find visible xpath`: локатор в коде есть и корректен → **система**; локатор битый/устарел/опечатка/ не найден → **ошибка автотеста**.
  - `expected X got Y`: тест ожидает верно, предусловия корректны, а система вернула другое → **дефект**; тест ждёт неверного / битые данные в тесте → **ошибка автотеста**.
- **Подтвердить** несомненные категории локусом в коде (файл:строка), если применимо.

**6.4. Вывод по каждому тесту**:
- тип = один из {система, автотест, дефект};
- **подкрепление**: сообщение из API и/или `файл:строка` из git;
- если не удалось подтвердить однозначно → пометить «не подтверждено (без однозначного кода)», рекомендация дать человеку.
