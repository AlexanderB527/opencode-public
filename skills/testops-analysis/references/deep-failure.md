# Режим: глубокий разбор

> Часть скилла `testops-analysis`. Общие правила — `../SKILL.md`.

## 🔴 Пути: где лежат скрипты, эталоны и артефакты

`<QA_HOME>` — корень скилла (определяет `scripts/_paths.py`: env `QA_HOME` → родитель папки `scripts/`).
Артефакты прогонов — вне репозитория: `~/.qa-artifacts/` (env `QA_ARTIFACTS_ROOT`, флаг `--root`).

| Что | Где |
|---|---|
| скрипты, правила | `<QA_HOME>/scripts/`, `<QA_HOME>/config/` |
| эталоны (кэш) | `~/.qa-artifacts/etalons/<TEAM>/etalon_<тип>.txt` — скачивает `fetch_etalons.py` из ветки `qa-analysis-data` |
| командные Jenkins-джобы | `<QA_HOME>/config/team_jobs.json` (версионируется) |
| персональные джобы (fallback) | `~/.qa-artifacts/autotesters.json` |
| артефакты прогонов | `~/.qa-artifacts/launches/…`, `~/.qa-artifacts/reruns/…` |

**Полная картина** — пути, поток данных, справочник скриптов, диагностика: `toolkit-guide.md`.
**Контракты артефактов** (кто пишет / кто читает): `../config/contracts/README.md`.

## Назначение

Пользователь передаёт список упавших тестов (номера `@04.02.01.01`, названия, ID тест-кейсов, ссылку на launch, либо «разбери все упавшие в launch / на странице Confluence»). Задача — для КАЖДОГО теста:

1. **Понять, почему упал** (корневая причина, не поверхностный симптом).
2. **Предложить решение** (что чинить, где именно — файл:строка, и с каким критерием готовности).

Опора — **два независимых источника**, сверяемых между собой:
- **git** (репозиторий `AUTOTEST/sfa`): сам код теста — локаторы, ожидания, предусловия, page objects.
- **Confluence**: бизнес-контекст, причины падений из прогонов, описания тест-кейсов, известные изменения логики.

Глубокий разбор НЕ ограничивается «типом» (система/автотест/дефект) — это отдельный аналитический шаг поверх/вместо классификации: результат — корневая причина + конкретное решение.

## Критические правила

1. **Источники истины — git и Confluence, не догадка.** Любой вердикт «тест устарел / логика изменилась / локатор битый» подкрепляется локусом в коде (`файл:строка`) и/или Confluence-страницей. Без подкрепления — «не подтверждено».
2. **Каждый тест — отдельный блок** «Причина + Решение». Не сжимать похожие падения одной строкой; похожесть свести в «связанные падения» внутри блока, но блок на тест сохраняется.
3. **Сообщение из API — первичный факт**, из него извлекается упавший шаг и текст ошибки. Сверяться с кодом этого шага.
4. **Глубина через git-лестницу** до пометки «не подтверждено» (поиск файла — до 4 попыток, Шаг 3; лестница глубокого разбора — ровно 3, Шаг 4).
5. **Confluence — вторичный контекст, не замена коду.** Бизнес-описание помогает интерпретировать, но непротиворечивость ожиданий теста проверяется по коду.
6. **Ничего не менять** — скилл read-only (Git Context / atlassian / testops только для чтения). Не публикует в Confluence без явной просьбы; не пишет код.
7. **Реальные причины** — без выдумки. Нет данных → «не подтверждено» + что нужно человеку, чтобы закрыть вопрос.
8. **Неясно → спросить, а не гадать.** Неоднозначность, блокирующая прогресс, снимается вопросом пользователю, а не угадыванием: блуждание по репозиторию стоит дороже одного вопроса. Триггеры и формат — раздел «Уточнения».

## Инфраструктура артефактов и локальные скрипты

Тяжёлую механику (пагинация, сверка множеств, гейты, публикация) выполняют
скрипты из `<QA_HOME>/scripts/` — они пишут артефакты на диск, агент читает результат.

**Полное описание:** поток данных, политика хранения, справочник скриптов —
`toolkit-guide.md`. **Контракты артефактов** — `../config/contracts/README.md`.

> **Правило №0 — не писать код с нуля.** До написания любого скрипта: `glob *.py`
> в `<QA_HOME>/scripts/` и использовать готовое. Свой скрипт — только если шаг
> реально не покрыт, и только в `~/.qa-artifacts/temp/`.

## Уточнения (спрашивай, не блуждай)

Неоднозначность — это НЕ повод угадывать и продолжать поиск вслепую. Если дальнейший шаг блокируется нехваткой информации, а самостоятельное получение исчерпано — задать вопрос.

**Когда спрашивать (триггеры):**
- набор тестов неоднозначен (большой launch, неясно: все / только FAIL / подмножество);
- лестница поиска в git провалена (L1–L2 пусты, либо исчерпан лимит 4 попыток) — спросить: директория команды, название файла, фрагмент кода, ссылка на тест;
- команда/директория неизвестны и не выводятся из TestOps;
- message пустое / инструмент недоступен / вердикт спорный, и код не даёт ответа;
- гипотеза пользователя не подтвердилась и непонятно, что имелось в виду.

**Как спрашивать:** один конкретный вопрос с кратким контекстом «что уже сделано / что не найдено» и 2–3 вариантами для быстрого ответа. Несколько несвязанных неоднозначностей — задать батчем (до 4 вопросов), не по одному.

**Чего НЕ спрашивать:** то, что можно получить самому — message и шаги из TestOps, команду из результата, локатор из git. Вопрос — только после собственных попыток (BP1, лестница поиска).

**Режим без интерактива (субагент):** если интерактивный вопрос недоступен — НЕ продолжать угадывание: вернуть маркер
```
## Status: clarification_needed
## Question for User
<один конкретный вопрос>
## Context for Decision
<что выполнялось, почему нужен ответ, варианты>
```
и остановиться до получения ответа.

## Вход

- `tests` — преобразованный список: номера (`@04.02.01.01`) или названия тестов, или ID тест-кейсов из TestOps; может прийти ссылкой на launch / страницу Confluence, одиночным номером или диапазоном.
- `launch_id` (опц.) — если указан, сначала добрать по нему: определения/шаги тест-кейсов + status/message.
- `git_repo` (опц., дефолт): `workspace=AUTOTEST, repository=sfa`.
- `parent_page_id` / `confluence_target` (опц.) — если разбор привязан к опубликованной странице падений.

## Выход

- По каждому тесту — блок: `@номер — название`, статус, ошибка (message + упавший шаг), **Причина** (корневая, с `файл:строка`/Confluence-ссылкой), **Решение** (конкретное действие + критерий готовности + кому), статус подтверждённости.
- Сводка в конце: подтверждено / не подтверждено + что запросить у человека.
- По умолчанию — результат в чат. Публикация в Confluence — ТОЛЬКО по явной просьбе.

## Шаги

### Шаг 1 — Зафиксировать список тестов
Уточнить переданный набор. Если пришла ссылка на launch → шаг 2. Если списоĸ номеров — нормировать к виду `@NN.NN.NN`, убрать дубли, сохранить порядок. Если набор неоднозначен (большой launch, неясно какие именно: все / только FAIL / подмножество) — задать уточняющий вопрос ДО разбора (раздел «Уточнения»), не догадываться и не начинать разбор вслепую.

### Шаг 2 — Собрать исходные данные падения (TestOps / launch)
Для заданных тестов извлечь:
- определение тест-кейса: `testops_testcase_get` / `testops_testcase_get_details` (шаги, предусловия, ожидания);
- если работаем с launch: `testops_launch_list_test_results(launch_id, page, size=100)` с гейтом хвоста — status + `message` по каждому тесту;
- сценарий/шаги: `testops_testcase_get_scenario` — порядок шагов, где какой шаг упал.

На выходе — «факт-карта» теста: шаги, ожидаемый результат, реальный message, упавший шаг.

### Шаг 3 — Сопоставить тест с кодом (первичный адрес)
**Gate BP1**: git-поиск начинается ТОЛЬКО после факт-карты Шага 2 (есть message + упавший шаг). Нет message → вернуться в Шаг 2, не идти в репо.

Приоритет поисковых ключей (по убыванию точности):
1. **точный номер** теста (`@10.05.03.01`);
2. **префикс группы** (`10.05.03`) — для поиска всех файлов группы;
3. **фрагмент текста ошибки / локатор / текст кнопки из message** — самый точный ключ к упавшему шагу;
4. **название теста**;
5. **суть шагов**.

**Гипотеза пользователя = первый grep.** Если пользователь дал предположение («нужно найти пользователей, для которых кнопка "Мои" отображается») — начать с grep по его тексту (кнопка/локатор) в step definitions и POM + проверить предусловия теста (какие пользователи создаются, в каком состоянии).

**Лестница (строго по порядку, угадывать папку ДО исчерпания L1–L2 запрещено):**
- **L1.** `bitbucket_grep(workspace=AUTOTEST, repository=sfa, query=<номер>)` И `query=<префикс группы>` — прямое вхождение;
- **L2.** `bitbucket_search_code(... query=<название/фрагмент ошибки/локатор/текст кнопки>)`;
- **L3.** локальный `rg -n "<номер/префикс/фрагмент>" <клон sfa>` (если путь к клону известен) ИЛИ точечный `bitbucket_list_directory_content(path=<подозреваемая директория>)` с опорой на **сегменты номера**: `@A.BB.CC.DD` ≈ вложенность папок — для группы ищи подпапку с сегментом `BB.CC` под `features/Tests/**`. ЗАПРЕЩЕНО обзор всего дерева для поиска файла.

**Команда как маршрутизатор:** если Team известна (из TestOps или подсказки пользователя) — сначала директория команды (`features/Tests/<Team>/**`) и фильтр `Team` в grep/search_code.

**Стоп-правило (анти-блуждание):** максимум 4 попытки поиска файла. После исчерпания — НЕ продолжать перебор и НЕ угадывать: перейти в раздел «Уточнения» (спросить: директория команды, название файла, фрагмент кода, ссылка) и выдать промежуточный отчёт (что сделано / что найдено / что не найдено). Саб-агент для перебора структуры — только после 2 проваленных шагов лестницы и с чётким ТЗ (вернуть файлы, содержащие номер/префикс), а не «найди сам».

Связать найденный файл с тестом; пометить найден/не найден. Соглашение «номер ↔ файл» может быть неполным — поиск эвристический.

### Шаг 4 — Глубокий разбор каждого теста (Причина)
Найдя файл, проанализировать в контексте сообщения об ошибке:
- **Локатор/шаг**: найти упавший шаг в коде. Локатор существует? корректен? актуален для текущей разметки? `Unable to find visible xpath` + битый/неактуальный локатор → тест/страница изменились.
- **Ожидание**: что тест ждёт (expected) vs что вернула система (got). Ожидание верное, а данные иные → логика/бизнес изменились (дефект или устаревший тест). Ожидание неверное → ошибка теста.
- **Предусловия/данные**: тест строит данные сам или ждёт из среды? Внешние зависимости (данные, тайминги) → стабильность.
- **Стабильность**: та же ошибка в первичном и rerun → стабильно (логика/тест); только в одном → флак/окружение.
- **Исключение очевидного окружения**: есть таймауты/500/сеть → указать, но не останавливаться на этом, если код даёт более точную причину.

**Лестница попыток (ровно 3, только после неё «не подтверждено»):** 1) grep по номеру, 2) search_code по названию/телу, 3) локальный `rg` по клону / точечный list по пути + чтение файла. Сбой инструмента → повторить 1 раз; при повторном сбое → «инструмент недоступен» (отдельный статус, не «не подтверждено»).

### Шаг 5 — Confluence-контекст (вторичный)
`confluence_search` / `confluence_get_page` по теме теста, модулю падений, известным прогонам. Использовать для: интерпретации ожидаемого поведения (бизнес-правило), подтверждения «логика изменилась» (известные изменения), поиска похожих разборов. Результат — ссылка на страницу в блоке Причины. НЕ искать сведения, которые уже есть в коде (код — главный источник по ожиданиям).

### Шаг 6 — Сформировать блок «Причина + Решение»
Для каждого теста:
```
@N — Название теста
Статус: FAIL/BROKEN/SKIP
Ошибка: {message из API}
Упавший шаг: {шаг} — {статус/время}
Причина: {корневая, подкреплена файлом:строка и/или Confluence-ссылкой}
Решение: {что чинить + где + как проверить (критерий) + кому}
Связанные падения: @N1, @N2 (если есть)
Подтверждено: да / нет (если нет — что запросить)
```

**Причина** — не «система/тест/дефект», а корневой вердикт, например:
- «Локатор `xpath=".//td[@headers='a2']"` устарел: в строке таблицы под конкретным заголовком нет ячейки — файл:строка; разметка страницы изменилась (Confluence ref)».
- «Тест ожидает статус `Ожидает обработки`, а система отдаёт `Продажа в SFA` — предусловие не создаёт объект в нужном состоянии (файл:строка); бизнес-логика перехода изменилась (Confluence ref)».

**Решение** — конкретное: «Обновить локатор в page object X:строка → искать по новому заголовку col N; критерий: тест проходит в прогоне Y». «Поправить предусловие в строке Z: перед шагом создавать объект через API/UI в статусе K; критерий: стабильный PASS 2 запуска подряд». «Завести дефект на переход статуса — воспроизводится стабильно в обоих прогонах». С указанием адресата (QA-автоматизатор / разработка продукта / окружение).

### Шаг 7 — Сводка, статусы и финальный чек-лист
В конце: `Разобрано: {N} | Подтверждено: {X} | Не подтверждено: {Y} | Инструмент недоступен: {Z}`. Для не подтверждённых — список и что нужно запросить у человека (номер файла, доступ, актуальную ошибку, страницу Confluence).

### Шаг 8 — Запись подтверждённых причин в базу

Глубокий разбор даёт evidence (`файл:строка`, дефект, Confluence-страница) — это то,
что переводит причину из `suspected` в `confirmed`. Запись — через публикацию результата:

```powershell
py -X utf8 <QA_HOME>\scripts\publish_results.py --team <TEAM> --type <HF|QG|RM> --launch-id <id> --push
```

- Если по прогону уже публиковался результат с рераном, повторная публикация обновит
  причины (evidence и статус), счётчики не раздуются.
- Причины без evidence остаются `suspected` — это нормально и честно.
- База читается при следующем разборе: `fetch_results.py --team <TEAM>`.

**Финальный чек-лист перед ответом:**
- каждый переданный тест имеет блок «Причина + Решение» (Шаг 6);
- вердикт подкреплён (`файл:строка` / Confluence-ссылка) ИЛИ помечен «не подтверждено» с указанием, что запросить;
- если блоков нет вовсе (данные/поиск провалились) — НЕ пустой ответ: частичный отчёт (что сделано / что найдено / что не найдено) + вопрос пользователю из «Уточнений»;
- при Server error / lostResponse / обрыве — продолжить с последнего успешного шага, не начинать заново; при отмене пользователем — сохранить накопленное и кратко отчитаться.

## Контрольные точки

- **BP1** (после шага 2): факт-карта каждого теста собрана (шаги, ожидания, message, упавший шаг).
- **BP2** (после шага 4): у каждого теста найдено место в коде ИЛИ исчерпана лестница поиска файла (4 попытки, Шаг 3) и задан вопрос пользователю (не угадывание дальше).
- **BP3** (после шага 5): Confluence-контекст сверен, где применимо.
- **BP4** (после шага 6): вердикт подкреплён `файл:строка`/ссылкой ИЛИ помечен «не подтверждено». Решение конкретное, с критерием.

## Краевые случаи

| Ситуация | Действие |
|---|---|
| Тест не найден в git (4 попытки) | «не подтверждено (файл не найден)» + вопрос пользователю (раздел «Уточнения»): директория команды, название файла, ссылка |
| Сбой git-инструмента | статус «инструмент недоступен», не «не подтверждено» |
| Один паттерн ошибки у многих тестов | блоки у каждого, но «Связанные падения» сведены; глубокий разбор общей причины 1 раз, остальные ссылаются |
| Message пустой | проверить шаги/Confluence; иначе «без сообщения — не подтверждено» |
| Ожидание vs данные: не ясно, чьё верно | решать через git (актуальны ли ожидания/локаторы); если не решается — «не подтверждено» |
| Падение из-за окружения + код валиден | указать окружение как причину, НО с обоснованием (нет признаков битого теста); отдать инфраструктуре |
| Разбор большого launch без уточнения набора | уточнить у пользователя, какие тесты разбирать (все / только FAIL / подмножество) |

## Границы

- НЕ пишет и НЕ правит код (read-only).
- НЕ продолжает угадывание структуры после исчерпания лимита попыток — переходит к вопросу пользователю (раздел «Уточнения»).
- НЕ публикует в Confluence без явной просьбы (по умолчанию результат в чат).
- НЕ раскладывает по трём типам система/тест/дефект как самоцель — это промежуточный шаг к корневой причине.
- НЕ даёт вердикт без подкрепления; без данных — «не подтверждено» + что запросить.
- НЕ пересчитывает полный прогон — анализирует только переданный список тестов.
